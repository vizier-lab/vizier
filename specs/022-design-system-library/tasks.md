# Tasks: Design System Library

**Input**: Design documents from `specs/022-design-system-library/`

**Prerequisites**: [plan.md](plan.md), [spec.md](spec.md), [inventory.md](inventory.md) (approved scope), [research.md](research.md), [data-model.md](data-model.md), [contracts/](contracts/), [quickstart.md](quickstart.md)

**Tests**: No TDD was requested. Automated checks are part of the plan instead: `npm test` (every story rendered headless with axe; research R9), `npm run typecheck`, `npm run lint:tokens` and `npm run build-storybook`. Each tier ends with a task that runs them.

**Organization**: Grouped by user story. US2 (repository + submodule, P1) comes before US1 (catalogue, P1), because the catalogue lives in that repository. Within US1, components follow the inventory tiers T1 → T4. Each tier ends with its barrel export and checks. User Story 4 (keeping in step with FigCraft) was dropped: the repository has no FigCraft integration (FR-023).

## Format: `[ID] [P?] [Story] Description`

- **[P]**: can run in parallel (different files, no dependency on an unfinished task).
- **[Story]**: US1–US3 from spec.md (US4 was dropped with the FigCraft sync).
- **Paths**: `design/…` is the `vizier-lab/design` repository, checked out at `design/` in vizier (a nested repo until T016 makes it a submodule). Other paths are in vizier.
- **Inventory ids** (B#, D#, X#) are the rows of [inventory.md](inventory.md). Each component task restates its row, so it can be done without reopening the inventory.
- **FigCraft** is only read (FR-013c), through the `figcraft` MCP with the FigCraft app open on `Vizier.figcraft` (`C:\Users\ganes\OneDrive\Dokumen\Vizier.figcraft`, readable from WSL at `/mnt/c/Users/ganes/OneDrive/Dokumen/Vizier.figcraft`). Never edit or save it.
- **Story content** uses vizier's own names (Archivist, Scout, `vector-db-review`). Never the dev-only offline provider; use Ollama as the example local provider.

## Dependencies & Execution Order

### Phase Dependencies

- **Setup (Phase 1)** → **Foundational (Phase 2)**: tokens, styles, icons and the source block block every component.
- **US2 (Phase 3)** needs Phase 1 (something to push) and is best done right after Phase 2, so every later commit lands in the real repository. The first push needs the maintainer's go-ahead.
- **US1 (Phase 4)** needs Phase 2. Inside it: foundations/icons/brand first (in parallel), then tiers strictly in order T1 → T2 → T3 → T4. Within a tier: components → barrel → checks.
- **US3 (Phase 5)** needs at least tier T1 of US1. Run it after US1 so the check covers everything.
- **Polish (Phase 7)** needs all stories.

### Within US1

- A component may depend only on components of its own tier or lower (data-model InventoryEntry). Same-tier dependencies are spelled out in the task ("Depends on T…"), and those tasks are not marked [P].

### Parallel Opportunities

- Phase 1: T003, T004 and T007 alongside T005/T006.
- Phase 2: T009, T011, T012 and T013 alongside each other once T008 has written `tokens.css`.
- US1: all foundation pages and brand pieces together; inside each tier every [P] component task together (different directories; the barrel is a separate task per tier).

## Implementation Strategy

### MVP first

1. Phase 1 + Phase 2 (repository, tokens, icons).
2. US2 (repository published, submodule pinned).
3. US1 **foundations, brand and tier T1 only** → **stop and review**: the maintainer checks the review flow on real entries (theme switch, states, source block, PNG) before the remaining ~120 components are built the same way.
4. T2 → T3 → T4, each tier reviewed as it lands.

### Incremental delivery

Each tier ends with a green `npm test` and a commit, so the catalogue is reviewable after every tier, and review findings shape the next tier rather than arriving all at the end.
