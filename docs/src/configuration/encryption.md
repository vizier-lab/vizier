# 2.14 Encryption at Rest

Vizier stores credentials and secret values in its embedded SQLite database. Those values — agent secrets, provider API keys and access tokens, custom-provider keys and header values, Discord/Telegram bot tokens, the Brave Search key, MCP environment values, and shell environment values — are **encrypted at rest** with a workspace key that is not stored in the database. Everything else stays readable: names, masks, timestamps, provider endpoints and base URLs, integration transport/command/arguments/URL/safe-search flags, shell paths and images, and agent models and prompts.

The protection is field-level and transparent. Every existing workflow — agent `get_secret`, the WebUI and HTTP API, provider calls, channel connections, addons and MCP tools — behaves exactly as before. No endpoint, screen or configuration key was added.

## Key sources and precedence

The key is resolved once at startup, in this order:

| Order | Source | Behaviour |
|---|---|---|
| 1 | `VIZIER_ENCRYPTION_KEY` | Base64 of exactly 32 bytes. A set-but-empty or malformed value is a startup error; it never falls back. |
| 2 | `VIZIER_ENCRYPTION_KEY_FILE` | Path to a key file. Missing, unreadable or malformed is a startup error; Vizier never creates this file. |
| 3 | `<workspace>/.runtime/encryption.key` | Loaded when present. Generated only when it is absent **and** there is no protected value. |

A fresh install needs no setup: the file is generated on first start, with owner-only permissions where the platform supports it, and startup never prompts. The key never enters the database, an API response, a log line, telemetry or an error message.

### Key file format

```text
vizier-key-v1
<base64 of exactly 32 bytes>
```

The file is UTF-8 and a trailing newline is allowed. Vizier never overwrites it. The default location is next to the database, inside the workspace's `.runtime` directory.

## What happens when the key is wrong or missing

| Situation | Result |
|---|---|
| No key and no protected data | Generate a key and continue. |
| No key but protected data exists | Startup stops: `encrypted data exists but no encryption key was found; set VIZIER_ENCRYPTION_KEY or restore the key file…`. No key is generated. |
| Malformed operator key | Startup stops: `encryption key is malformed: expected 32 bytes encoded as base64`. Nothing is written. |
| Explicit key file missing/unreadable | Startup stops naming the path. Nothing is written. |
| Key does not match the stored data | Startup stops: `encryption key does not match this data`. Nothing is written. |
| Restore the correct key | Startup succeeds and every value is available again. |
| A protected value was altered outside Vizier | The read fails with an integrity error naming the table/record/field; no partial value is returned. |

Changing the key by hand without re-encrypting the data is **not supported** and fails closed. There is no key rotation, recovery code or escrow in this release.

## Backups and restores

The key is as important as the data:

- **Back up the key separately from the data.** A copy of the workspace without the key cannot read its protected values.
- **Restore data and key together** on another machine with a compatible installation; everything works.
- **Restore data only** and Vizier refuses to start with the missing-key message rather than silently starting empty or generating a new key.
- A backup taken while Vizier is running contains protected values; checkpointing the database is not required, but the key must be included in the backup plan.

Container deployments must persist the workspace (the key sits inside it), or supply the key through `VIZIER_ENCRYPTION_KEY`/`VIZIER_ENCRYPTION_KEY_FILE`. If the workspace is ephemeral and the key is not persisted, startup fails instead of regenerating over the data.

If the key is lost, the protected values are **unrecoverable**. They cannot be decrypted, re-created from the ciphertext, or regenerated by Vizier. Restore the key from its backup, or restore a pre-encryption backup and re-enter the values.

## What is protected, and what is not

Protected at rest:

- agent secret-store values;
- saved provider API keys and access tokens, including ChatGPT's session token;
- custom-provider API keys and every custom request-header value (header names stay readable);
- Discord and Telegram bot tokens;
- the Brave Search API key;
- every value in an MCP server's environment map;
- every value in an agent's local or Docker shell environment map;
- the stored global shell environment map, where present.

Not protected — by design:

- conversation history and transcripts, agent memory and CORE documents, uploaded session files, task text, dream journals, notification summaries, usage records;
- user password hashes and API-key hashes (already one-way);
- `.vizier.yaml`, environment variables, and any credential passed inside a field that is not classified as secret (for example a token embedded in an MCP command argument);
- the workspace key file itself when it is stored beside the data, and full-disk/OS-level encryption.

### The shell-environment exception

Local and Docker shell environment values are encrypted at rest but remain part of the agent configuration returned to people allowed to view or edit that agent, exactly as before. Making them write-only is a separate change. They are not a substitute for the agent secret store.

## Threat model

This feature protects **data at rest**: backups, synced folders, stolen disks, database files read by another local account, and support bundles. It does **not** protect against a compromised host, a running Vizier process, a malicious operator with access to the key, memory inspection, swap, or a copy of the entire workspace that includes the key.

With the default key beside the data, a copy of the whole workspace is not protected; only a copy of the data **without** the key is. Operators who need stronger separation should supply the key from a secret manager or a mounted file and keep it out of the data backup.

## Upgrades, downgrades and the 1.0 path

On first start after upgrading from a pre-encryption release, Vizier converts every existing plaintext in-scope value in place, with no operator action. The conversion is idempotent and resumable, and it reclaims the old plaintext from SQLite free pages and the WAL (via `secure_delete`, checkpointing and `VACUUM`) before normal operation begins. A failed conversion stops startup without writing the completion marker; the next start retries.

Downgrade is **not supported**: an older release cannot read protected values and must not overwrite them. Restore a pre-upgrade backup to downgrade.

The conversion is the last pre-1.0 migration point. It is tracked for removal in [#82](https://github.com/vizier-lab/vizier/issues/82). Installations coming from a pre-encryption release must start the last pre-1.0 release once before upgrading to 1.0.0; otherwise the later release will not convert their plaintext. The cipher, key handling, key id, AAD and envelope reader are permanent.

## Diagnostic scan

Support output and logs never contain a key or a protected value. To check a workspace yourself, stop Vizier and scan the database, WAL and any log you intend to share:

```sh
for value in provider-secret-abc123 custom-secret-abc123 brave-secret-abc123 \
             mcp-secret-abc123 shell-secret-abc123; do
  printf '%s: ' "$value"
  grep -a -c "$value" <workspace>/.runtime/vizier.db || true
  grep -a -c "$value" <workspace>/.runtime/vizier.db-wal 2>/dev/null || true
done
grep -c "$(sed -n '2p' <workspace>/.runtime/encryption.key)" /tmp/vizier.log
```

Expect `0` for every line. Do not scan session history or the agent request/debug log for a value an agent set with `set_secret`: the set input is part of the agent's script and is documented as the one set-operation exception (`specs/027-agent-secrets`). Values set through the WebUI or HTTP API never enter a transcript.
