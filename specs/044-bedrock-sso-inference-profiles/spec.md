# Feature Specification: AWS Bedrock over SSO with Application Inference Profiles

**Feature Branch**: `044-bedrock-sso-inference-profiles`

**Created**: 2026-11-02

**Status**: Draft — clarifications closed 2026-11-02 (Q1–Q4 answered); **ready for `speckit_plan`**

## Context

Vizier already ships Amazon Bedrock as a first-class provider (spec `034-aws-bedrock-provider`): one saved connection — access key ID, secret access key, optional session token and region — signs every chat, embedding and image request with AWS Signature Version 4 and talks to the region's Bedrock runtime endpoint. That provider deliberately supports exactly one credential form, a static IAM access key pair, and refuses everything else by naming the supported form. Its own specification records that decision as an explicit, temporary exclusion: shared profiles, SSO, instance profiles, task roles and assumed roles are out of scope "for this iteration".

Two facts about how Vizier's AWS users actually run Bedrock make that single form insufficient.

**Organisations on IAM Identity Center issue no static keys.** Their people sign in through the Identity Center portal, receive short-lived role credentials, and sign in again when those expire. Long-lived access keys are often forbidden outright. For such a person the existing provider is not merely inconvenient — it cannot be connected at all, because there is no key pair to paste.

**Model access is granted per team through Application Inference Profiles.** An inference profile is a named, separately metered and separately budgeted resource with its own ARN, created in the Bedrock console. The same foundation model routinely appears several times under different profile ARNs — one per team, per environment, per budget. The model catalogue cannot know these ARNs: they are per account, private, and change without notice. Today the only way to use one is to type the raw ARN into one agent's model field, which loses the readable name, the limits and the capabilities, gives no list to choose from, produces a silent, unvalidated typo, and has to be repeated for every agent that needs it.

This feature adds a **second Bedrock provider** — not a mode of the existing one — that authenticates through IAM Identity Center and whose model selection is a **managed list of custom models identified by ARN**. The two providers coexist: an operator with static keys keeps the connection they have, untouched; an operator on SSO connects the new one. Both speak the same Bedrock wire protocol, so the chat machinery, the SigV4 signer, the model-id encoding and the error translation are shared rather than duplicated; what differs is where credentials come from, how they are stored, and how the model list is built. The new provider offers **full parity** (clarification Q1): chat, memory embeddings and image generation, all through the one SSO connection, exactly as the static-credentials provider does. Credentials come from a role the sign-in resolves; the session itself lives in **Vizier's own encrypted storage** and nowhere else (clarification Q2), so no AWS CLI is needed, nothing is written to `~/.aws`, and the connection keeps a **profile name** of its own as the handle for that stored session.

The value is access and precision: people who are not allowed to hold AWS keys can use Bedrock at all, and everyone can select the exact inference profile their team is billed for, by the name they gave it, from a list that is validated once instead of typed per agent.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Sign in with AWS SSO and talk to Bedrock (Priority: P1)

A person in an organisation that uses IAM Identity Center opens Settings › Providers, finds the Bedrock provider that signs in with SSO, and follows the setup guide on its form: they give the Identity Center start URL (or pick an existing SSO session), the region the Identity Center instance lives in, then the account and the role they want to use — both chosen from what their sign-in is actually entitled to, not typed blind. Vizier shows them a short code and a URL; they confirm in a browser on any machine. When they return, the form reports the sign-in succeeded, the account and role it resolved, and when the session ends. They create an agent, choose this provider, pick a model, and send a message. The agent answers through Bedrock, with the credentials of that role.

**Why this priority**: Nothing else in this feature has value without it. It is also the whole reason the feature exists: a person who cannot hold an access key currently cannot use Bedrock in Vizier at all.

**Independent Test**: With an Identity Center instance, one assigned account and role, and Bedrock model access, connect the SSO provider from Settings › Providers alone (no AWS CLI, no shell) and hold a multi-turn conversation with an agent on that provider. Confirm the saved connection reports the account, the role and the session's expiry, and that the same agent keeps replying across turns without asking to sign in again.

**Acceptance Scenarios**:

1. **Given** no SSO Bedrock connection exists, **When** a person opens Settings › Providers and searches for Bedrock, **Then** both Bedrock providers are listed — the existing static-credentials one and the SSO one — each with its own name, its own state and its own connect form, and connecting one leaves the other exactly as it was.
2. **Given** the SSO provider's connect form is open, **When** the form is shown, **Then** an inline "How to connect" guide lists the steps to obtain each value (find the Identity Center start URL, choose the region of the Identity Center instance, pick the account and role, confirm the sign-in, enable the models or inference profiles in Bedrock), with the exact IAM policy the role needs, and links to the AWS pages it names and to the Vizier provider documentation.
3. **Given** a person enters a start URL and an SSO region, **When** they start the sign-in, **Then** Vizier shows a short code and a URL to confirm, waits for the confirmation, and then reports success together with the resolved account, role and session expiry, or the reason it failed.
4. **Given** a successful sign-in, **When** the person reaches the account and role selection, **Then** only the accounts their identity is assigned to and the roles granted in the selected account are offered, and the chosen pair is saved with the connection.
5. **Given** a saved SSO connection and an agent whose provider is the SSO Bedrock provider, **When** the agent is sent a message, **Then** it replies through Bedrock and the reply is stored in history like any other reply.
6. **Given** an agent on the SSO provider, **When** the conversation runs across several turns, **Then** earlier turns, the agent's system prompt and its CORE document are carried to the model exactly as for the existing Bedrock provider.
7. **Given** a person who has never configured AWS SSO tooling, **When** they connect the provider, **Then** they are never required to run a shell command, install the AWS CLI, hand-edit a file, or paste a temporary access key. Vizier itself runs the sign-in and keeps the session in its own encrypted storage, never in a file the AWS CLI owns and never in a file that must be maintained to someone else's format (clarification Q2), so the person sees a form, a code and a confirmation — nothing else, and nothing appears under `~/.aws`. The connection keeps a **profile name** of its own as the handle for that stored session; the session and its token are encrypted inside Vizier, the profile name is only the name.
8. **Given** the person's sign-in is denied, times out, or the code is confirmed twice, **When** the attempt ends, **Then** the form reports which of those happened, no partial or empty connection is saved, and the attempt can be retried without leaving the form.
9. **Given** an existing static-credentials Bedrock connection, **When** this feature ships, **Then** it keeps working unchanged, is never migrated, restarted or re-validated by it, and its agents' behaviour is identical.

### User Story 2 - Choose the team's Application Inference Profile by name (Priority: P1)

A person saves an SSO Bedrock connection, then adds the inference profiles their account was given: they paste the ARN from the Bedrock console, give it the name their team uses, and save. The provider's model picker now lists those entries with their names, and an agent chooses one by name. When that agent runs, the ARN is sent to the endpoint unchanged, so the traffic, the metering and the budget land on that profile and nowhere else. The list is entered once and is reused by every agent on that provider.

**Why this priority**: This is the second half of the request, and it is what makes the connection usable in a multi-team AWS account. Without it the SSO provider could only reach catalogue models, which is precisely the case the profiles are meant to replace.

**Independent Test**: With an SSO connection, save two inference profiles whose names are distinguishable but whose underlying foundation model is the same; point two agents at the two profiles; send each a message and confirm both reply, and that the console's per-profile metrics show the two profiles were used, not one shared model.

**Acceptance Scenarios**:

1. **Given** the SSO provider with no custom model saved, **When** the model picker is opened for that provider, **Then** it lists the catalogue's Bedrock models as before, with an explicit way to add a custom model by ARN.
2. **Given** an inference profile ARN pasted into the add-model form, **When** the person gives it a name and saves, **Then** the entry is stored on the connection, listed with that name for every agent on that provider, and selectable without typing an ARN again.
3. **Given** an agent whose model is a saved ARN entry, **When** a turn runs, **Then** the ARN is sent to the runtime endpoint exactly as stored, as one encoded path segment, and nothing substitutes the underlying foundation model id.
4. **Given** a saved ARN entry with no name, **When** it is listed, **Then** it is shown by its own profile id taken from the ARN rather than as a blank row, and the ARN itself remains visible wherever the person can verify it.
5. **Given** a pasted value that is not a Bedrock inference-profile ARN (a foundation-model ARN, an ARN for another AWS service, a bare model id, an ARN with a missing segment), **When** the person saves it, **Then** the value is refused with a message naming the expected shape and no row is created.
6. **Given** an ARN already saved on the connection, **When** the same ARN is added again, **Then** the duplicate is refused and the existing entry, with the name it already has, is unchanged.
6a. **Given** the add-model form, **When** the person reaches the pricing step, **Then** they pick the underlying model from a searchable list of the catalogue's Bedrock chat models rather than typing an id, the ARN and the chosen model are saved as a pair, and the usage of that entry is then priced from the chosen model.
6b. **Given** an entry saved with an ARN but no model chosen, **When** an agent uses it, **Then** the turn runs, the usage row records the ARN and token counts with **no cost**, and the entry is visibly marked as pricing-not-set rather than showing 0.
7. **Given** an ARN whose region segment differs from the connection's Bedrock region, **When** it is saved or first used, **Then** the person is told the two regions disagree and which one to change, instead of a transport error presented as a mystery.
8. **Given** a saved ARN entry, **When** an agent's limits and capabilities are computed, **Then** any values the person supplied for that entry are used, and where none were supplied the entry is treated as unknown rather than as unsupported, so context checkpoints and tool warnings keep their existing behaviour.
9. **Given** an ARN that was deleted or renamed in AWS, **When** an agent uses it, **Then** the provider's own error is surfaced naming the model, and the connection and other entries stay usable.
10. **Given** several agents on different ARNs of the same connection, **When** they run, **Then** each sends its own ARN and none is shared, cached or defaulted from another.

### User Story 3 - The session refreshes itself, and says so when it cannot (Priority: P2)

A person does not think about the SSO session while they work. Role credentials expire hourly and the session itself after a working day; Vizier renews the credentials from the live session in the background as requests need them, so ordinary conversations never interrupt. When the session finally ends, the next turn says so plainly — "your SSO session ended, sign in again" — with a link to the connect form that only asks for the confirmation code, not for the start URL, account and role again. Work that runs without a person watching (scheduled tasks, dreams, background jobs, sub-agents) never sits waiting for a sign-in: it fails with that same explanation and the agent reports itself unhealthy until the session is renewed.

**Why this priority**: Expiry is not an edge case on SSO; it is the normal state of the world within hours. A feature that works only until the first expiry is a support queue. It is separable from the first two stories, though, and does not block them.

**Independent Test**: With a short-lived session (or by waiting out an expiry), run turns until the role credentials pass their expiry without any re-sign-in and confirm the turn succeeds. Then invalidate the session itself and confirm the next interactive turn names the session as the cause and offers re-sign-in, while a scheduled task fails immediately rather than hanging, and the agent's health reports the failure until a new sign-in is made.

**Acceptance Scenarios**:

1. **Given** a connection whose role credentials have expired but whose session is still valid, **When** an agent sends a request, **Then** the credentials are renewed before the request is sent and the turn succeeds without any person's involvement.
2. **Given** several agents on the same connection sending requests at the same moment as an expiry, **When** they are renewed, **Then** the connection is renewed once and every request uses the fresh credentials, without a burst of token calls.
3. **Given** a session that has ended, **When** an interactive turn runs, **Then** it fails with a message that names the session (not the credentials, the region or the model) and points at the re-sign-in action.
4. **Given** a session that has ended, **When** a scheduled task, a dream cycle, a background job or a sub-agent runs, **Then** it fails promptly with the same explanation and does not retry in a loop or wait indefinitely.
5. **Given** an ended session, **When** the person re-signs in, **Then** the account and role already saved are reused, no other field has to be entered again, and the agents that use the connection resume without a Vizier restart.
6. **Given** a session revoked in AWS (signed out of all devices, role assignment removed), **When** the next request runs, **Then** the failure names the cause and the agent does not present a broken state as a working one.
7. **Given** a turn in which the provider answers that the credentials are not valid, **When** Vizier retries, **Then** it retries at most once after renewing, and a second failure ends the turn with the provider's explanation rather than a retry storm.

### User Story 4 - Memory and images use the same SSO connection (Priority: P2)

A person sets an agent's memory embeddings to the SSO Bedrock provider, leaves the model empty or picks an embedding model, and the agent's memories are indexed through the same stored session. The same for image generation. Nothing about the connection is configured twice, and a session that ends affects all three capabilities together. Because the person can also name their team's inference profiles, an entry they saved for chat is offered where they would look for it — but never silently sent to an embed or image call it cannot serve, and never in place of a working default.

**Why this priority**: Clarification Q1 settled the scope as full parity. Chat-only SSO would leave an SSO shop with no working memory recall unless they kept a second vendor just for embeddings, which is precisely the arrangement this feature exists to remove. It is independently testable and independent of the inference-profile list.

**Independent Test**: With only an SSO connection, embed and search a distinctive memory phrase, and generate one image; then let the session end and confirm all three capabilities report the same cause and recover together after one re-sign-in. Separately, add an inference-profile entry and confirm that the embedding and image model pickers still resolve to a foundation model they can actually invoke.

**Acceptance Scenarios**:

1. **Given** an agent whose embedding provider is the SSO Bedrock provider and whose model is empty, **When** a memory is saved, **Then** its passages are embedded through that connection, `memory_search` finds them, and the model used is the provider's documented embedding default — exactly as with the existing Bedrock provider.
2. **Given** an agent whose image-generation provider is the SSO Bedrock provider, **When** an image is requested, **Then** it is generated through the same connection and saved as an attachment like any other generated image.
3. **Given** the SSO connection and the static-credentials connection both exist, **When** an agent's embedding or image provider is chosen, **Then** the two are distinguishable options and each uses its own credentials.
4. **Given** a session that ended, **When** an embedding or image call runs, **Then** it fails with the same session explanation as chat, and writes no wrong-sized vector and no broken file.
5. **Given** a saved inference-profile entry on this connection, **When** an embedding or image model is chosen, **Then** the profile ARN is not used as an embedding or image model in its place: the picker offers the foundation models those capabilities support, and the ARN stays available for chat.
6. **Given** a person who selects an ARN for an embedding or image call anyway, **When** the call is attempted, **Then** it is refused before the request with a message naming the capability and the models that do work, rather than failing deep inside Bedrock.
7. **Given** any agent not using this provider, **When** the feature ships, **Then** its embeddings and images are unaffected and no reindex happens.

### User Story 5 - Operate it: who uses it, what it costs, how to remove it (Priority: P3)

A person rotates a role, changes account, changes the Bedrock region, re-signs in, or removes the connection. Vizier says who is affected before something is deleted, restarts exactly the agents that use this connection, prices this provider's usage separately from the static-credentials one, and never shows a token.

**Why this priority**: Necessary for the feature to be operable, but it reuses the existing provider-change, usage and delete-confirmation machinery, so it can land after the value-bearing slices.

**Independent Test**: Run a chat turn, check that the usage view attributes it to this provider (not the other Bedrock provider), change the region and confirm only this connection's agents restart, then delete the connection with two agents using it and confirm the affected list is shown first and both agents report the actionable cause afterwards.

**Acceptance Scenarios**:

1. **Given** both Bedrock providers connected, **When** usage is viewed, **Then** each provider's turns are attributed to their own connection and priced, and neither is merged into the other: a catalogue model is priced from the catalogue, and an ARN entry is priced from the model the person picked for it in the entry's own dropdown (FR-034a), with an explicit price overriding it, and visibly unpriced when nothing was picked or the picked model is no longer in the catalogue.
2. **Given** a saved SSO connection used by agents, **When** its region, account or role is changed, **Then** exactly those agents restart and the next turn uses the new values with no Vizier restart.
3. **Given** a delete request for a connection agents use, **When** the confirmation is requested, **Then** the affected agents are named before anything is removed, and after removal each names the missing connection as the cause.
4. **Given** any screen, API response, log line or error, **When** the connection is inspected, **Then** the start URL, account, role, both regions and the session expiry are visible, and no token, code or secret is ever shown.

### Edge Cases

- **SSO region versus Bedrock region**: the Identity Center instance and the Bedrock runtime legitimately live in different regions. The connection therefore holds two regions; every message about a region must say which one it means, and choosing one must never silently change the other.
- **A person in several accounts or with several roles**: the chosen account and role are part of the saved connection, and changing either is a connection change that restarts its agents.
- **Two Vizier processes on one machine** (the desktop edition and a server, or two profiles) sharing one workspace: each reads the stored session through the workspace key, so a renewal by one is visible to the other only through the store, and a sign-out by either must surface to both as a session problem rather than as a wrong key or a wrong model. The per-connection renewal lock (FR-014) is per process, so a renewal racing across two processes must stay idempotent against the store.
- **The user also uses the AWS CLI for other work**: the two sessions are independent by design. A `aws sso login` in a terminal does not reach Vizier, and a sign-in in Vizier does not reach the CLI; a person who needs both approves the browser twice. Neither tool can break the other by signing out.
- **The stored session is unreadable — workspace key missing, rotated, or belonging to another workspace**: the connection reports that the session cannot be read, names the profile, and offers a fresh sign-in (FR-009f); it never falls back to an empty session, never crashes and never deletes the connection, its custom models or its agents.
- **Sign-in performed on another machine**: the code and URL are shown so the confirmation can happen anywhere, which must not be blocked by requiring a local browser.
- **Clock skew** between the machine and AWS: an expiry that appears to be in the past, or a signature rejected as skewed, must read as a time problem rather than as a wrong password.
- **A role without the invocation permission**, or one whose permission covers only catalogue models: the provider's own refusal is surfaced with the action name it names.
- **Model access not enabled for the account**, or the ARN belonging to a different account than the role: the provider's error is authoritative and is passed through, naming the model.
- **An ARN pasted with surrounding whitespace, a console URL instead of an ARN, or a line break from a table copy**: refused with the expected shape rather than stored verbatim.
- **An ARN whose profile was deleted while an agent still points at it**: the turn fails naming the model; the connection, its other entries and other agents are unaffected.
- **Session expiry between a request being sent and its answer**: the answer is kept, the turn is not re-run from scratch, and only the next request renews.
- **The same foundation model both as a catalogue id and as a saved ARN entry**: both remain selectable and are not merged, because they are metered differently.
- **Deleting the SSO connection while a turn is in flight**: the turn ends with an actionable error, and nothing partial is stored.
- **An empty custom-model list on a connection**: the picker must still lead to the catalogue models rather than showing an empty state that looks like a failure.
- **The model a person wants is not in the dropdown**: a model newer than the loaded catalogue, or one models.dev does not carry. The entry can still be saved with the ARN alone (pricing-not-set), or with a hand-entered price, or the person refreshes the catalogue and re-picks. An ARN entry is never refused, and an agent on it is never blocked, for want of a model to pair it with.
- **A selected model disappears from the catalogue after the entry was saved**: the entry keeps its stored id, shows pricing-not-resolved naming it, uses no price without saying so, and is not silently re-pointed at a different model. Re-picking or hand-entering a price fixes it.
- **A person pairs an ARN with a model from a different family or region on purpose** (because that is the rate their account is billed at): the pairing is accepted, because the dropdown prices the entry and does not judge the ARN (FR-034a.6). Region disagreement remains FR-024's job, read from the ARN alone.
- **A catalogue refresh lands while entries exist**: labels and prices of existing entries update from the refreshed catalogue, no entry is renamed, rewritten or dropped, and a hand-entered price is left exactly as it was.
- **An ARN uses the system form or an unusual partition**: `inference-profile/` and `application-inference-profile/` are both accepted, in every AWS partition, and both are sent to the runtime unchanged. Accepting one form more does not make either form eligible for embedding or image (FR-033a).
- **A person picks an inference-profile ARN as an embedding or image model**: the ARN is a chat resource. The picker does not offer it for those capabilities, and naming it directly is refused before the request with the models that do work — so a memory index is never written with a vector from a call that could not have produced one.
- **The profile name and the stored session disagree** — the session row is present but unnamed, or a profile name points at a session that is gone: the connection reports which half is missing and offers a fresh sign-in, rather than reporting a credential failure. The name is a handle, not the secret (FR-009e).
- **A person who pastes temporary credentials into the existing provider** and then wonders why they expire hourly: this feature must not make the two forms easier to confuse; each connection states its own credential form.

## Requirements *(mandatory)*
### Functional Requirements

**A second provider, beside the first**

- **FR-001**: Vizier MUST offer AWS Bedrock over IAM Identity Center as a **separate, independently connectable provider** with its own identifier, display name, credential fields, setup guide, connection state and model list, distinct from the existing static-credentials Bedrock provider, in Settings › Providers, in every provider and model picker, and through the HTTP API.
- **FR-001a**: The existing Bedrock provider's setup guide MUST keep answering for the existing provider only, while the new provider answers with its own guide; the provider listing MUST NOT end up reporting the same guide, or no guide, for either.
- **FR-002**: The two providers MUST share the Bedrock wire behaviour — the conversation protocol, the model-id path encoding, the regional runtime endpoint, the request signer and the error translation — as one implementation with two credential sources, not as two copies.
- **FR-003**: Connecting, changing, re-signing in to or deleting either provider MUST NOT alter, restart, re-validate or migrate the other, and an agent on one MUST be unaffected by any change to the other.
- **FR-004**: Existing static-credentials connections, their agents and their stored configuration MUST behave exactly as before, with no migration and no reindex.

**Connecting through IAM Identity Center**

- **FR-005**: A connection MUST be creatable from the Bedrock provider's form alone — with no shell command, **no AWS CLI installed or required**, no hand-edited file, nothing written under `~/.aws` and no pasted temporary key — by supplying an Identity Center start URL (or an already-registered session), the SSO region, an account and a role. The sign-in Vizier performs MUST be complete on its own (FR-006), not a wrapper around someone else's CLI.
- **FR-006**: The sign-in MUST use the AWS SSO device-authorization flow: Vizier requests a sign-in, shows the person a verification URL and a short code, waits for the confirmation, and reports success, failure or timeout with the reason.
- **FR-007**: After a successful sign-in the account and role MUST be chosen from what that sign-in is actually entitled to — the accounts assigned to the person's identity, and the roles granted in the chosen account — not typed blind, and the chosen pair MUST be stored with the connection. A free-text fallback MUST exist only where the authorization does not list them.
- **FR-008**: The connection MUST store the start URL, SSO region, Bedrock region, chosen account, chosen role and the session's identity, and MUST be able to re-sign in reusing them, so an expired session asks for a confirmation code and nothing else.
- **FR-009**: Vizier MUST keep the SSO session in **its own workspace storage, protected by the project's existing at-rest secret encryption** (the same boundary that protects provider credentials today), and MUST be able to renew role credentials from it, so a Vizier restart does not force a new sign-in while the session is still valid. The session MUST NOT be written to, read from, or reconciled against the AWS CLI's cache or any other tool's file under `~/.aws` (FR-009a).
- **FR-009a**: The stored session MUST be encrypted at rest by Vizier as a secret-bearing field: it is written only through the existing encrypted-storage path, is unreadable without the workspace key, and follows the project's key rules — a wrong or missing key fails closed and is never a reason to regenerate a key over protected data. A plaintext session on disk MUST NOT be possible by configuration.
- **FR-009b**: The session and its token MUST never be written to a file, exported, logged, echoed in any API response or shown on a screen; only the non-secret identifiers (start URL, both regions, account, role, profile name, expiry) may be displayed. Reading the session is scoped to the connection that owns it.
- **FR-009c**: Session lifecycle is Vizier's own. A sign-out performed inside Vizier MUST delete the stored session; a session ended on the AWS side (sign-out of all devices, revoked role assignment, expired refresh token) MUST be detected on the next request and reported as a session problem, never as a wrong key, a wrong region or a wrong model. Nothing about the connection may depend on another process signing in or out.
- **FR-009d**: The role credentials Vizier derives from the session MUST be cached in memory only, renewed before expiry and serialized per connection (FR-013, FR-014); they MUST NOT be written to disk, so the stored session is the only persisted credential material.
- **FR-009e**: Vizier MUST keep a **profile name** as the readable handle for the stored session, so the person can tell two connections apart and so logs and error messages can name one without exposing it. The profile name MUST be non-secret, MUST survive a restart, MUST address exactly one stored session per connection, and MUST NOT be a credential: two profile names MUST resolve to two independent sessions, and a connection whose stored session is gone MUST report that by profile name and offer a fresh sign-in rather than presenting a credential failure.
- **FR-009f**: Losing or rotating the workspace encryption key MUST leave the affected connections reporting an unreadable stored session and offering a re-sign-in — never a silent empty session, never a crash, and never an automatic deletion of the connection or its custom models.
- **FR-010**: The **SSO region and the Bedrock region MUST be separate settings of the connection** (the Identity Center instance and the Bedrock runtime may legitimately be in different regions), MUST default to each other when only one is given, and every validation message MUST say which of the two it concerns.
- **FR-011**: Region validation MUST reuse the existing Bedrock region rules for both regions, and MUST NOT guess either.
- **FR-012**: Starting a sign-in, completing it, discovering accounts and roles, renewing credentials and validating a model ARN MUST each be able to run without an agent, and MUST NOT require the person to save a half-configured connection first.

**Session lifetime and renewal**

- **FR-012a**: The connection test MUST prove the permission the provider actually needs, **by a minimal invoke against the model or inference profile the person selected** (clarification Q4), not by a listing call. It MUST run without saving a half-configured connection, MUST report success with the model it invoked, and MUST surface the provider's refusal verbatim when the role lacks the permission or the model access is not enabled.
- **FR-012b**: Because the test is an invoke, the minimal policy shown in the guide and in the documentation MUST consist of `bedrock:InvokeModel` alone; any listing permission MUST be documented as optional and MUST NOT be required for the connection to save or for the test to pass.
- **FR-013**: Role credentials MUST be renewed from the live session automatically, before they expire, without any person's action and without an extra request per turn when the cached credentials are still valid.
- **FR-014**: Renewal MUST be serialized per connection, so concurrent requests at an expiry produce one renewal and all of them use the fresh credentials.
- **FR-015**: When a request is refused because the credentials are not valid, Vizier MUST renew once and retry once; a second failure MUST end the turn with the provider's explanation, and MUST NOT loop.
- **FR-016**: When the session itself has ended, every request MUST fail with a message that names the **session** as the cause and points at the re-sign-in action, and MUST NOT be reported as a wrong key, a wrong region or a wrong model.
- **FR-017**: Work that runs without a person present (scheduled tasks, dreams, background jobs, sub-agents, inter-agent messages) MUST fail promptly with that same session explanation and MUST NOT wait for, prompt for or block on a sign-in.
- **FR-018**: An interactive turn that fails for an ended session MUST leave the agent available, and its health MUST report the failure until a sign-in succeeds, after which its agents resume without a Vizier restart.
- **FR-019**: Re-signing in MUST affect exactly the agents using this connection, through the existing provider-change path, and MUST NOT restart agents on any other provider.

**Custom models: Application Inference Profiles**

- **FR-020**: The provider MUST support a **managed list of custom models on the connection**, each entry holding an Application Inference Profile ARN, a display name, and optional per-entry limits and capabilities (context window, output limit, tool calling, image input), plus the optional **pricing field of FR-034a, which is a selection from a list rather than free text**. Every field beyond the ARN is optional, so an entry can be added by pasting an ARN alone.
- **FR-021**: The list MUST be editable from the provider's page and MUST be shared by every agent on that connection: adding, renaming, editing or removing an entry MUST be one operation, not one per agent.
- **FR-022**: The provider's model picker MUST list the saved custom entries with their names alongside the catalogue's Bedrock models, and choosing one MUST store and send that entry's ARN.
- **FR-023**: An ARN MUST be validated on save against the **AWS inference-profile ARN shape**, which accepts **both** resource types — `inference-profile` and `application-inference-profile` — with the profile identifier segment present, the partition segment one of the AWS partitions (`aws`, `aws-cn`, `aws-us-gov`, `aws-iso`, `aws-iso-b`), and the region and account segments present. The shape follows AWS's own pattern `arn:<partition>:bedrock:<region>:<account>:(inference-profile|application-inference-profile)/<profile-id>`. Anything else — a foundation-model ARN, another service's ARN, a bare model id, a truncated ARN, a console URL, a value with stray whitespace — MUST be refused with a message naming the expected shape, and MUST NOT be stored. **This feature is about the application form**: `application-inference-profile` MUST be accepted on equal footing with the system-defined form, and neither form may be refused merely for being the other.
- **FR-024**: An ARN whose region segment differs from the connection's Bedrock region MUST be reported as a mismatch naming both regions at save time or first use, and MUST NOT be sent as if it were valid.
- **FR-025**: A duplicate ARN on one connection MUST be refused, leaving the existing entry and its name untouched.
- **FR-026**: An entry with no name MUST be displayed by the profile identifier taken from its ARN, and the ARN MUST remain visible where the person can verify it; nothing MUST be displayed as a blank or unidentifiable row.
- **FR-027**: An ARN MUST be sent to the runtime endpoint **unchanged**, as one encoded path segment, with no substitution of the underlying foundation-model id and no rewriting of its region or account.
- **FR-028**: Context window, output limit and capabilities for an entry MUST be resolved in the existing order (agent override, then the entry) and, where neither supplies them, MUST be treated as **unknown** rather than as unsupported (clarification Q3: optional, unknown when left empty; never inferred from the ARN, never required), so context checkpoints, attachment handling and tool warnings behave as they do for any model with unknown values.
- **FR-029**: Removing an entry that agents still use MUST be refused or must name those agents first, following the existing in-use confirmation behaviour for provider changes.
- **FR-030**: The catalogue's own Bedrock models MUST remain selectable on this provider, so a connection can reach both a catalogue model and a profile ARN without a second provider.
- **FR-031**: An ARN that AWS rejects (deleted profile, wrong account, permission not covering it) MUST surface the provider's own error naming the model, and MUST leave the connection and its other entries usable.
- **FR-032**: The custom-model list MUST be stored on the connection and MUST be independent of the catalogue refresh, so a catalogue refresh never renames, rewrites or drops an entry.

**Capabilities, configuration and operations**

- **FR-033**: The provider MUST supply **chat, memory embeddings and image generation** to the same extent as the existing Bedrock provider (clarification Q1), all through the one connection, with no capability requiring a second sign-in. It MUST be offered as a choice for all three wherever the choice is made — WebUI pickers, HTTP API and defaults — and must behave exactly as the static-credentials provider does for each.
- **FR-033a**: **An inference-profile ARN is a chat model, not an embedding or image model.** The ARN MUST NOT be substituted for the foundation model that an embedding or image call needs: the embedding and image pickers keep offering the foundation models those capabilities support (including their documented defaults when the field is left empty), the saved ARN entry stays listed for chat, and a call that names an ARN for embedding or image generation MUST be refused before the request with a message naming the capability and the models that do work. Vizier MUST NOT attempt to derive an embedding or image model out of an ARN. **A wider ARN grammar does not widen this ban**: both resource types are chat models, and neither may be offered or accepted for embedding or image generation.
- **FR-033b**: Where a person leaves the embedding or image model empty on this provider, the existing documented defaults MUST apply unchanged (`amazon.titan-embed-text-v2:0` and `amazon.nova-canvas-v1:0` in this codebase's current defaults), and the provider's own refusals for an unsupported family MUST pass through, so an SSO-only setup reaches memory recall and image generation with no extra configuration.
- **FR-034**: Every answered chat completion on this provider MUST record its token counts and be priced from the catalogue, and MUST be attributed to **this** provider so its usage is never merged with the static-credentials provider's. For an entry that resolves to a catalogue model by ARN alone (a catalogue id saved as a custom entry, FR-030), pricing follows that model's catalogue cost exactly as for any other catalogue model.
- **FR-034a**: **An ARN entry carries one optional pricing field, and its value is chosen from a list, not typed.** The list is the **Bedrock model list Vizier's own catalogue already holds** — the `amazon-bedrock` entry of the models.dev-sourced catalogue, the same list that already serves this provider's chat model picker (203 models in this workspace, each carrying `cost`, `limit`, `modalities`, `attachment` and `tool_call`). It is not a free-text field, not a new list, and not fetched from AWS. When the entry is created, the person **pairs the ARN with one model from that list**, and the pair is what the entry stores.
- **FR-034a.1**: The list MUST be the catalogue's Bedrock chat models as currently loaded, MUST show at least the model's display name and its id, and MUST be searchable so a person can find a model by name or id without scrolling 200 rows. **It MUST reflect a catalogue refresh** without the person re-adding entries: an entry stores the chosen model **id**, and the model's name and price are re-resolved from the catalogue each time they are displayed or used, so a refreshed catalogue updates the label and the price of every existing entry and never orphans one.
- **FR-034a.2**: **The field stays optional (clarification Q3 is unchanged).** An entry may be saved with an ARN alone and no model selected. Such an entry MUST be usable for chat immediately, and its usage is recorded as **unpriced** — the same `None`-cost representation the codebase already uses — never zero and never a figure derived from the ARN. The provider's UI MUST show that entry as "pricing not set" so the omission is visible rather than silent.
- **FR-034a.3**: **Price resolution, in this order, once a model is selected:** (1) the selected model's catalogue cost, re-resolved at use time, is the price; (2) if the selected id is no longer in the catalogue — a model withdrawn between versions, or a catalogue that has not been refreshed — the completion is recorded as **unpriced** and the entry is flagged "pricing not resolved" naming the missing id, so the person can re-pick it. An explicit price is still permitted as the escape hatch for this case (FR-034a.4), and nothing else is inferred.
- **FR-034a.4**: **An explicit price overrides the catalogue.** If a person enters a price by hand for the entry, that price is used and no catalogue lookup happens — it wins over the selected model's cost. This exists for the case a person knows the effective rate and the catalogue does not, and it MUST NOT be silently overwritten by a later catalogue refresh.
- **FR-034a.5**: **Pricing never blocks inference.** Whatever the selection resolves to — a price, an explicit price, or nothing — the turn MUST run and its tokens MUST be recorded. A missing or stale price is a reporting fact, never a refusal, never a retry, and never a reason to disable the entry or the agent.
- **FR-034a.6**: **The selection prices the entry; it does not validate the ARN and it does not fill in limits.** The ARN's own validation stays exactly as FR-023 defines it, over the ARN string alone: the selected model MUST NOT be used to accept, reject, rewrite or region-check an ARN, and a mismatched pair (an ARN in one region with a model id from another family) MUST NOT be rejected on that ground — FR-024 stays the only region check and it reads the ARN. Nor does the selection populate context window, output limit, tool-calling or image-input: those stay per-entry optional fields under FR-028, which is unchanged, so a selected model's limits are **not** copied onto the entry and an entry with no limits given is still treated as unknown, not as the selected model's values.
- **FR-034b**: **An unpriced entry must be stated, not silently priced as zero.** Wherever the price cannot be resolved — field left empty, selected id gone from the catalogue, catalogue unavailable on a cold start before its seed loads — the completion is recorded as unpriced (`None` cost), the usage row still carries provider, model (the ARN) and token counts, and the provider's own UI flags the entry as "pricing not set" or "pricing not resolved" with the id that failed. 0 completions may be costed at zero, and 0 may carry a fabricated figure.
- **FR-034c**: **No control-plane call and no extra permission is introduced for pricing.** The price MUST NOT be obtained by calling Bedrock (`GetInferenceProfile`, `ListFoundationModels` or any other control-plane or runtime operation); the only AWS request the feature makes is the invocation itself, plus the invoke-based connection test (FR-012a). The minimal policy therefore stays `bedrock:InvokeModel` alone (FR-012b). The dropdown is populated from Vizier's own catalogue, so opening it costs no AWS call either.
- **FR-035**: Secrets — the session and its token, the derived role credentials, the device code and any client secret — MUST never appear in an API response, a screen, a log line, an error message or a telemetry attribute; the start URL, regions, account, role, profile name and expiry MAY be shown so a person can identify the connection. **At-rest protection is now Vizier's own obligation and not a borrowed one**: the stored session is encrypted with the workspace key (FR-009a), Vizier is its only holder, and there is no other copy anywhere — the derived role credentials live in memory only (FR-009d), and nothing about the session appears under `~/.aws` (FR-005, FR-009).
- **FR-036**: The provider MUST work everywhere a provider works: every channel, scheduled tasks, the dream cycle, sub-agents, background jobs, inter-agent messages, handovers and checkpoints.
- **FR-037**: Startup, provider and agent builds, the scheduler and dreams MUST NOT make any AWS request beyond what the existing Bedrock provider already does; a sign-in and an account/role listing happen only when a person asks for them, and a renewal only when a request needs it.
- **FR-038**: The in-form setup guide MUST be supplied as data on the provider listing and rendered by the existing generic form, with no provider-specific branch in the form, and its full text MUST be the new section of the provider documentation, reachable through a stable link.
- **FR-039**: The documentation MUST cover creating the SSO connection, the difference between the SSO region and the Bedrock region, the role's required permissions, the expiry and re-sign-in behaviour, what background work does when the session ends, and how to add, name, validate and remove an inference-profile ARN — including the note that the ARN is per account and cannot come from the catalogue.
- **FR-040**: Deleting the connection MUST name the agents that use it before removing anything, and MUST leave those agents reporting the missing connection as their cause rather than failing obscurely.
- **FR-041**: The provider's failures MUST each read differently enough to act on: sign-in denied, code expired, session expired, role not assigned, permission missing for an action, model access not enabled, profile not found, region mismatch, throttling, and service unavailability.
- **FR-042**: A failed request MUST NOT crash an agent, lose results already produced in the turn, or store a half-written assistant message.

### Key Entities

- **SSO Bedrock connection**: the one saved entry for the new provider — start URL or session reference, SSO region, Bedrock region, chosen account, chosen role, session identity, session expiry, and the custom-model list. Secrets are write-only and encrypted; everything else identifies the connection.
- **SSO session**: the sign-in state obtained by the device flow, holding what is needed to renew role credentials while it is valid, and its expiry. It lives in **Vizier's own encrypted storage** (clarification Q2), keyed to one connection and readable only through the workspace key; it has no counterpart on disk anywhere else, and Vizier records its **profile name**, start URL, account, role and expiry alongside it.
- **SSO profile name**: the non-secret, readable handle for one stored session — what a person types to recognise a connection, and what an error message or a log line may name without exposing the session. It is not a credential: showing it is harmless, and it carries no key material. It is what lets two connections to the same account and role stay distinguishable while their secrets remain encrypted.
- **Role credentials**: the short-lived access key, secret and session token derived from the session for the chosen account and role, cached until shortly before they expire.
- **Custom model entry**: one Application Inference Profile on the connection — its ARN, its display name, optional context window, output limit, tool-calling and image-input capabilities, whether the person edited them, and its optional **priced-by pairing**: one model chosen from the catalogue's Bedrock chat list at the moment the entry is added, stored as a model id and re-resolved from the catalogue on every display and every use, plus an optional hand-entered price that overrides it. The pairing decides how the entry's usage is costed (FR-034a); it does not validate the ARN and does not supply limits (FR-034a.6).
- **Inference profile ARN**: the identifier AWS assigns to a profile — partition, service, region, account, resource type and profile identifier — which is what an agent's model field holds for such an entry.
- **Agent model selection**: an agent's provider id and model value, where the model value is either a catalogue id or a saved entry's ARN, resolved at build time into the endpoint, credential and limits.
- **Usage record**: one row per answered completion on this provider, carrying the provider id (this one, never the other Bedrock provider), model and token counts, and **a cost that is either a figure or explicitly absent**. An absent cost means "unpriced" — a stated fact, not zero — and happens exactly when an ARN entry supplied no explicit price and no foundation-model id that the catalogue could price (FR-034a, FR-034b). Embedding and image calls on this provider are recorded under the same provider id with their own model.

## Assumptions

- The new provider has its own identifier and display name, derived from the existing Bedrock id by a form that names the identity method (for example `amazon-bedrock-sso`, shown as "Amazon Bedrock (SSO)"); the exact strings are chosen at planning time and are not part of this specification's contract beyond being distinct and stable.
- The existing provider stays exactly as it is: static access keys only, its own id, its own guide, its own connection. This feature adds; it does not convert, merge or migrate.
- Only the IAM Identity Center (SSO) credential form is added. Shared `~/.aws` profiles, instance profiles, ECS task roles, assumed-role chaining outside Identity Center, credential-process plugins and Bedrock API keys (bearer tokens) remain out of scope, and the existing provider's messages about them stay accurate — except that the existing provider's "SSO is unsupported" message MUST point at this new provider once it ships, instead of leaving the person with no next step.
- The sign-in uses the standard AWS SSO device-authorization flow against the public OIDC device endpoints, with Vizier's own registered client. **The session is kept in Vizier's own encrypted storage and nowhere else (clarification Q2 A); Vizier writes nothing under `~/.aws`, reads nothing from it, and does not require the AWS CLI to be installed.** No AWS SDK crate is added: the flow is handled with the project's existing HTTP client, and the session is protected with the existing at-rest encryption boundary and key handling rather than new machinery (Constitution I). This feature therefore adds no new place where secrets live — it reuses the one the project already has.
- Inference-profile ARNs are entered by a person, not discovered: Vizier does not call the Bedrock control plane to enumerate profiles, because that needs an extra permission and would make a settings page a metered AWS call. Enumeration may be offered later if the person grants the permission.
- **Pricing an ARN entry is a choice from a list, not a discovery and not a typed id** (requester's refined decision: "ada list model yang disupport sama bedrock terus tinggal sandingkan aja arn nya sama model yang dipilih"). The person pairs the ARN with a model picked from **the catalogue's own Bedrock chat list** — in this workspace that is the `amazon-bedrock` entry of the models.dev-sourced catalogue: 203 models, **0 of them without a `cost`**, and **none of them an embedding or image model**, which is what makes the list safe to offer beside an ARN. Prices come from that same catalogue, re-resolved each time, and an explicit price is the escape hatch. **No price is ever fetched from AWS, derived from the ARN, or inferred from the profile name**; no selection means unpriced, stated as such. Media pricing (OpenRouter's `openrouter_media.json`) is **not** involved: an inference profile is a chat resource (FR-033a), so no ARN entry is ever a speech, transcription or image model.
- **The dropdown is a pricing aid, not a second validator and not a limit source.** It is built from the same catalogue the picker already uses, so it adds no data source and no AWS call; it prices an entry and does nothing else. ARN shape and region stay judged from the ARN string (FR-023, FR-024), and context window, output limit and capabilities stay the entry's own optional fields under FR-028 — the pairing never copies them, so Q3's "unknown when empty" is preserved exactly.
- **The ARN grammar is AWS's, not this feature's.** Both resource types AWS accepts for inference profiles are in scope — `inference-profile` (system-defined) and `application-inference-profile` (application-defined) — because the feature exists for the application form and must not reject it. Partition coverage follows AWS too (`aws`, `aws-cn`, `aws-us-gov`, `aws-iso`, `aws-iso-b`). Widening the grammar is a correctness fix, not a scope change: it does not admit media models (FR-033a) and does not change what the runtime endpoint is asked to invoke (FR-027).
- Entries whose limits and capabilities were not supplied are treated as unknown (never as unsupported), matching how the catalogue treats unknown values, so existing checkpoint, attachment and tool-warning behaviour is unchanged; clarification Q3 offers the alternative.
- **This provider is full parity (clarification Q1 A): chat, memory embeddings and image generation.** All three ride the one connection and the one session; an SSO-only organisation needs no second provider for anything Bedrock can serve. The existing static-credentials provider keeps its own capabilities untouched. The one asymmetry inside Bedrock itself — an inference profile is a chat resource, not an embedding or image one — is handled by FR-033a rather than pretended away: an ARN entry serves chat, and embedding and image calls use the foundation models those capabilities support.
- **The role needs `bedrock:InvokeModel` only (clarification Q4 B).** The connection test is a minimal invoke of the model or profile the person selected, so the minimal policy documented and shown in the guide is that one action. `bedrock:ListFoundationModels` is optional, is not used by Vizier, and is not required for the test to pass — which is what makes the provider usable by a per-profile role. **The test therefore consumes tokens and counts against the account's model quota**: it is one small, billable request, it needs a selected target to run, and the guide and the button say so before it is pressed.
- One account and one role per connection: a person who needs two roles saves two connections under distinct names, and the catalogue's model list is the same for both.
- Streaming, prompt caching, Guardrails, provisioned throughput, Batch inference and Bedrock Agents remain out of scope, as recorded in spec `034-aws-bedrock-provider`.
- **The existing Bedrock id is compared by exact equality in the guide registry**, so "does this provider have a guide" must be decided per provider id once a second Bedrock id exists, not by matching the Bedrock family. This is a planning constraint, not a decision of this specification.
- **One stored session per connection, and no shared state with any other tool, now that Q2 is A**: Vizier is the only writer and the only reader of its own session store, so there is nothing to reconcile with the AWS CLI and nothing to corrupt. Two Vizier processes sharing one workspace read the same encrypted row; renewal must stay idempotent against the store even though the serialization in FR-014 is per process, and a person who also uses the AWS CLI holds two independent sessions by design.
- Verification is split by access, as with the existing provider: the automated suite covers the device-flow state machine, credential and session caching, ARN validation, the shared wire behaviour and the UI with fixtures and contacts no AWS endpoint; live behaviour is verified by a volunteer with an Identity Center instance and at least one inference profile, on a special release.

### Consequence notes (for the requester, not a refusal)

**Q1 = A — full parity.** Unchanged by the Q2 reversal. All three capabilities ride the one connection (FR-033), with the one real Bedrock asymmetry handled explicitly: an inference profile is a chat resource, so an ARN entry stays out of the embedding and image pickers and is refused before the request if named for them (FR-033a), and the documented embedding/image defaults apply unchanged (FR-033b). If an account's model access covers only profiles and not the underlying foundation models, embedding and image calls are refused **by AWS**, and Vizier passes that refusal through naming the model — parity does not create model access the account does not have.

**Q2 = A — Vizier owns the session.** Four consequences, all recorded rather than argued:

1. **Two independent sessions, if the person also uses the CLI.** A `aws sso login` in a terminal does nothing for Vizier, and a sign-in in Vizier does nothing for the CLI; someone who needs both approves the browser twice, once per tool. Neither can sign the other out. SC-017 (d) makes this measurable.
2. **The session is not shareable with any other tooling, and Vizier carries the whole lifecycle** — refresh, expiry detection, sign-out, and the decision about what happens when the workspace key is gone. There is no second implementation to lean on, and no tool that can repair it.
3. **At-rest security is entirely Vizier's responsibility.** The session is encrypted with the workspace key from the project's existing key handling (environment value, explicit key file, or the generated workspace key), and the security of the stored session is therefore exactly the security of that key and the workspace directory. If the key is lost, the session is unreadable — by design, and FR-009f/SC-019 require that to surface as a named, recoverable state rather than as data loss: the person re-signs in, and nothing is deleted. It also means a backup of the workspace that includes the key is, in effect, a backup of the live AWS session.
4. **What is not lost by choosing A.** A restart still needs no re-sign-in while the session is valid (SC-017 a) — that was the practical benefit people associate with a shared cache, and the own-store design delivers it without touching `~/.aws`. What is genuinely lost is only cross-tool session sharing: the "log in once with the CLI, Vizier follows" convenience. What is genuinely gained is a smaller secret surface — one store, one key, one owner, and no dependency on a third-party file format that can change under the feature.

**Q4 = B — invoke-based test.** Unchanged by the Q2 reversal. The documented minimal policy is `bedrock:InvokeModel` alone (FR-012b), and the test is **one small billable inference call** against a model or profile the person selected: it consumes tokens and model quota, needs a selected target before it is sent, and must report throttling or quota exhaustion as itself (SC-018).

**Q3 = A — no consequence worth flagging.** It matches the recommendation and withdraws nothing.
