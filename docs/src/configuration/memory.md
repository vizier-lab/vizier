# 2.11 Memory

Each agent's long-term memory is a set of **markdown documents on disk**, grouped into **bundles**, linked into a graph, and indexed for semantic search. The markdown is the source of truth; SQLite only holds a derived, reconcilable index so listing and graph queries never need to read the files.

## Layout

```
<workspace>/agents/<agent_id>/memory/
  default/                    # every agent has a "default" bundle
    index.md                  # auto-maintained table of concepts
    log.md                    # auto-maintained change log
    project-x.md
    people/
      alice.md                # concepts can be nested in subdirectories
  harry-potter/               # any other bundle, created on first write
    index.md
    log.md
    hogwarts.md
    ...
```

A **concept** is one `.md` file addressed by `(bundle, path)` where `path` is relative to the bundle and omits the `.md` extension (`people/alice`). Its **slug** is the file stem (`alice`).

## Concept document

```markdown
---
slug: hogwarts
title: Hogwarts — The Magical School
created_at: 2026-09-13T10:50:01Z
updated_at: 2026-09-13T10:50:01Z
agent_id: viz
bundle: harry-potter
tags: []
keywords: []
relations:
- gryffindor.md
- slytherin.md
attachments: []
attachment_count: 0
read_count: 0
---
## Hogwarts

Founded by [Godric Gryffindor](gryffindor.md) and [Salazar Slytherin](slytherin.md).
Compare with [[star-wars/jedi]] or the whole [[marvel]] bundle.
```

| Frontmatter | Maintained by | Notes |
|-------------|---------------|-------|
| `slug`, `title`, `bundle`, `agent_id` | Vizier | |
| `created_at`, `updated_at`, `read_count` | Vizier | `read_count` increments when the agent reads the concept via the memory tools |
| `tags`, `keywords` | you / the agent | Filterable in the WebUI and API |
| `relations` | Vizier | Re-parsed from the body on every read/write (self-healing) |
| `attachments` | Vizier | Session files attached to the memory; surfaced as session files when the memory is read |

### Links

| Syntax | Meaning |
|--------|---------|
| `[label](path/to/concept.md)` | Same-bundle link, relative to the bundle root |
| `[[bundle/slug]]` | Cross-bundle link to one concept |
| `[[bundle]]` | Cross-bundle link to a whole bundle (resolves to every concept in it when followed) |

Links to concepts that don't exist are kept as **broken edges** in the graph and shown as such; they heal automatically when the target is created.

`index.md` and `log.md` are regenerated by Vizier on every change — don't edit them by hand (edits to concept files *are* picked up: the index reconciles against the filesystem on list/graph operations).

## Agent tools

Available whenever the agent has an `embedding` + `indexer` configured:

| Tool | Description |
|------|-------------|
| `memory_write` | Create or update a concept. `bundle` defaults to `default` (a new bundle name creates it); `path` may nest (`friends/bob`); `tags` optional |
| `memory_read` | Semantic search across all bundles (or one), returns matching content |
| `memory_list` | No bundle → list bundles (name, count, last updated). With a bundle → paginated concept list |
| `memory_detail` | Full content of one concept by `(bundle, path)`; attaches its attachments to the session |
| `memory_follow` | Traverse links from a concept to the given depth |
| `memory_graph` | Nodes/edges: top level (bundles + cross-bundle edges) or within one bundle |
| `memory_delete` | Delete one concept (and its embedding) |
| `memory_delete_bundle` | Delete a whole bundle |

Before every reply, the user's message is also used to search memory (top 10, similarity ≥ 0.5) and any hits are shown to the model as `# Possible Related Memories`.

## HTTP API

All under `/api/v1/agents/{agent_id}/memory`:

| Method | Path | Description |
|--------|------|-------------|
| `GET` | `/` | List concepts. Query: `bundle`, `tags` (comma-separated), `offset`, `limit` (50), `sort_by`, `sort_order` |
| `POST` | `/` | Create: `{ "title", "content", "bundle"?, "path"?, "tags"?, "attachments"? }` |
| `GET` | `/query` | Semantic search. Query: `query`, `bundle`?, `limit` (10), `threshold` (0.5) |
| `GET` | `/bundles` | List bundles |
| `GET` | `/bundles/graph` | Bundle-level graph (`?search=` filters) |
| `GET` | `/{bundle}/graph` | Concept-level graph of one bundle |
| `GET` | `/bundles/{bundle}/export` | Download the bundle as `<bundle>.zip` |
| `POST` | `/bundles/import` | `multipart/form-data` with `file` (or `zip`) and optional `bundle` name |
| `DELETE` | `/bundles/{bundle}` | Delete a bundle |
| `GET|PUT|DELETE` | `/doc/{bundle}/{path}` | Read / update (`{ "title", "content", "tags"?, "attachments"? }`) / delete one concept |
| `GET` | `/related/{bundle}/{path}` | Linked concepts |
| `GET|POST` | `/history/{bundle}/{path}` | Version history of one concept: list (`?offset&limit`), one version (`?seq`), diff (`?to[&from]`); `POST { "seq" }` restores a version as a new one. See [REST API → Version history](../api-integration/rest-api.md#version-history-core-and-memories) |
| `GET|PUT|DELETE` | `/{slug}` | Legacy: same as `/doc/default/{slug}` |
| `GET` | `/{slug}/related` | Legacy related lookup in `default` |

## WebUI

Agent → **Memory**: browse bundles, view the graph, read/edit concepts with a markdown editor, export/import `.zip` bundles. Every concept's view has a **History** button: browse earlier versions (who saved, when, why), see a line diff against the previous version or between any two, and **Restore** an earlier version (or a deleted memory) as a new version. The same panel is available for `CORE.md` on the agent's **Core** page.

## Export / import

A bundle export is a zip of its directory (`*.md` concept files; `index.md`/`log.md` are rebuilt on import). Version history is not included in an export; each imported concept starts a fresh history with an `import` revision. Import writes every `.md` in the archive into the target bundle (`bundle` form field, default `default`), overwriting concepts at the same path, and embeds them with the agent's current embedding model. Archives with no `.md` files or with unsafe paths are rejected.

## Design notes

- Because the documents are plain markdown, you can `git`-track, grep, or hand-edit them. Vizier reconciles the index with the filesystem lazily.
- Vector embeddings are stored in the shared `document_index` table — see the dimension caveat in [Tools & Embedding](./tools-embedding.md#embedding-embedding).
- The full design lives in `specs/004-memory-open-format/` in the repository.
