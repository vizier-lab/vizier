# Contract: `POST /api/v1/agents/{agent_id}/btw`

**Feature**: `033-btw-side-chat`

Ask the agent one side-chat question beside one of the caller's own conversations. Synchronous: the response is the answer. Nothing about the call is saved except its usage (research R7).

## Auth

`require_auth` (JWT or API key), like every `/agents/{agent_id}/…` route. The caller must be able to view the agent (`user_can_view_agent`), else `403`. The host session is always `VizierSession(agent_id, HTTP(<caller username>, channel_id), Some(topic_id))`, so a caller can only ask beside their own conversations. The topic need not exist: a side chat beside a new conversation has no history to draw on and does **not** create the conversation.

## Request

```json
{
  "channel_id": "webui",
  "topic_id": "k3j9xq0a2b",
  "question": "Is the plan you just gave realistic for a team of two?",
  "turns": [
    { "question": "What did you mean by 'phase two'?", "answer": "The migration of …" }
  ]
}
```

| Field | Type | Required | Rules |
|-------|------|----------|-------|
| `channel_id` | string | yes | As in the topic routes |
| `topic_id` | string | yes | |
| `question` | string | yes | Trimmed; 1–4,000 characters |
| `turns` | array of `{question, answer}` | no (default `[]`) | Earlier turns of this side chat, oldest first; at most 8; each question 1–4,000, each answer 0–16,000 characters |

No `attachments` field; unknown fields are ignored.

## Responses

**200** — `APIResponse<BtwResponse>`:

```json
{ "data": {
    "answer": "For two people it's tight but doable if …",
    "stats": { "provider": "anthropic", "model": "…", "input_tokens": 1234, "output_tokens": 210, "…": "…" }
} }
```

| Status | Body (`APIResponse<String>`) | Meaning |
|--------|------------------------------|---------|
| 403 | `Access denied` | Caller cannot view the agent |
| 404 | `agent not found` | |
| 408 | `Agent response timeout` | No answer within the agent's `prompt_timeout` |
| 422 | the reason, e.g. `side chat is full — start a new one` | Validation (see Request) |
| 429 | `slow down — try again in {n}s`; also header `Retry-After: {n}` | Over 5 side-chat asks per 60 s for this user |
| 500 | `{kind label}: {message}` | The agent answered with an error, or its response channel closed (process restart) |
| 503 | `{kind label}: {message}` | `AgentUnavailable` (agent starting, failed, or restarted mid-answer) |

A rate-limited or invalid request is refused **before** anything reaches the agent, so it costs no tokens and is not queued.

## Guarantees

- Nothing is written to the conversation's history, its session detail (no creation, no title, no `is_thinking`), the turn journal, scratchpad, memory or notifications.
- The answer never comes from a tool: the model is offered no usable tool (research R5).
- The agent answers as itself: same system prompt, CORE.md, owner profile, documents, provider and model as the conversation.
- It sees the conversation as its next turn would (history since the last checkpoint, plus the checkpoint's handover), then `turns`, then `question`.
- One `usage_event` row per answered call, in the host conversation.
- Not resumable: a restart mid-answer is a failed request; the client may ask again.
- The request queues behind a turn already running in the same conversation, like any message, and is bounded by `prompt_timeout`.

## OpenAPI

Registered with `utoipa` beside `agent_chat` (`BtwRequest`, `BtwResponse`), so `webui/app/api/schema.d.ts` is regenerated by `scripts/openapi.mjs`.
