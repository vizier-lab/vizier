## G1 — the agent's hangover reaches the gate

**Landed.** `6927502c` (server field), `8ba36d93`/`9256036a` (pins), `8c17ce9`+`510ace8` (client chain).

**Chain, verified hop by hop [QA]:**
`crates/vizier-core/src/service/agents.rs:606` → `AgentDetail.live_voice_end_of_utterance_ms: u32`
(`:80`) → `webui/app/routes/chat.tsx:126` → `:559` → `Composer.tsx:73,105,476` →
`LiveVoiceControl.tsx:28,55,63,73,113` → `session.ts:67` (`deps.endOfUtteranceMs`) →
`session.ts:148` `new EnergyVad(3, hangoverOf(deps.endOfUtteranceMs))` → `vad.ts:33-36`.

**Provable here.** `vad.test.ts:104-110` already covers `hangoverOf`: `0 → 100`, `-50 → 100`,
`60_000 → 2000`, `250 → 250`, `undefined → 800`, `NaN → 800`; and `:122-124` builds a real client with
`endOfUtteranceMs: 250` and asserts `client.hangoverMs === 250`. All green in my run. **The last hop is
covered; the four hops before it are not.**

**Not provable here.** That a `GET /api/v1/agents/{id}` carrying `live_voice_end_of_utterance_ms: 250`
actually arrives in the browser and produces a 250 ms hangover. That needs a running server with an agent
whose setting is 250 — five hops between the assertion and the fact.

**Findings while reading.**

- **V1 — the clamp is silent, and only on the client.** The server sends the raw `u32`
  (`agents.rs:606`); nothing in `crates/` validates or clamps it (`grep end_of_utterance_ms crates/` → the
  field, the default 800, two default assertions, the two hops above — no bound). The client clamps to
  **100..2000** (`vad.ts:24-36`). So an agent configured at `60000` runs at 2000 and a `0` runs at 100,
  with **no word to anyone**: the setting on the agent page disagrees with the gate that runs.
  Owner: data (`@sepuh-be`) for a server-side bound or a named refusal; direction `@mamang-lead-be`.
  Not a release blocker, but it is the kind of gap that reads as "the setting does nothing" later.
- **V2 — one hop tested, four assumed.** Stated above; the fix is either a `live_voice_session` test that
  asserts the detail field, or an e2e assertion. I do not decide which.

## G2 — the filler word

**Landed.** `a03004fc` (session), `28160187` (the promise test).

**What is true by code [QA].** `FILLER_WORDS = ["okay","ya","mm","right"]` and `FILLER_AFTER_MS = 400`
(`session.rs:33,40`); armed at the start of every turn from `run_turn` (`session.rs:521`); sent only if the
generation still matches, the session is not stopped, **no real segment has been sent this turn**
(`reply_segments == 0`), and this turn has not spent its filler (`filler_spent`); dropped the same way as
any other segment (`send_speech`).

**Provable here (already covered, all green in my run).** Six assertions in `session.rs`:
one filler per slow turn and seq starts at 0 with the reply continuing 1,2,… (`:1419`);
one per turn across two turns (`:1471`); none for a quick answer (`:1491`); a full lane costs the filler and
not the reply (`:1512`); a filler that cannot be synthesised leaves the session working (`:1547`); and the
word list promises no duration (`:1448` — bans `sebentar`, `wait`, `moment`, `hold`, `soon`, `minute`, …).

**Not provable here.** That a person hears the word once, at about 400 ms, in the agent's voice, on a real
provider — the delay, the prosody and the join are all the provider's.

**Findings while reading.**

- **V3 — "dropped when the lane is full" is proven on the wrong lane.** `a_dropped_filler_never_costs_the_reply`
  builds `lane(1)` (`session.rs:1373`), a `tokio::sync::mpsc` with capacity 1 that stands in for the
  socket. The production drop lives in `TopicOutbound` with `LIVE_VOICE_SOCKET_BACKLOG = 16` (T021). The
  test proves the session tolerates a full channel; it does not prove the shipping drop path. Owner:
  data/Lead — either accept the weaker claim in words, or add a delivery test at the real lane.
- **V4 — the words are English, the session may not be.** `FILLER_WORDS` is a fixed English/interjection
  list, synthesised by the agent's TTS, while the session carries the conversation's language
  (`session.ts` `language`, FR-037). `right` read by an Indonesian voice is a coin toss the user will
  notice. Cosmetic, unmeasured, and a product call — not mine.
- **V5 — a fast second turn can silently get no filler.** `prepare_filler` sets `filler_ready` before the
  four `speak()` calls return (`session.rs:386-404`). A turn that starts while synthesis is still in
  flight sees an empty list and says nothing, with no test for that ordering. Low harm (a filler is
  cosmetic) but it means "always covered after 400 ms" is not what the code promises.
- **V6 — the state word changes at 400 ms.** The client moves to `speaking` on **any** `speech` frame
  (`session.ts:282`), so `Thinking` clears when the filler plays, before the answer exists. That is
  defensible — something *is* audible — but FR-042 says the indicator clears "when the first segment is
  heard", and a filler is now the first thing heard. Nobody wrote that down; it should be one line in the
  spec or one line in the code, not an accident. Owner: `@system-analyst` + Lead.

## G3 — the fast path and its retry

**Landed.** `3d655708` + `45c0b639` (`crates/vizier-core/src/agents/agent/mod.rs`).

**What is true by code [QA].** `fast_path_ok` (`:2368-2404`) requires **all** of: `req.spoken` (:2372),
`Content::Chat` (:2375), `chars().count() < 120` (:2381), no `/`, `\` or backtick (:2385), no work word
(:2389-2395), and no `AssistantPart::ToolCall` anywhere in the turn's history (:2397-2403). Decided once at
`:1018`, carried into `prompt_with` (:1187), used to empty the tool list on the first hop only
(`:1209-1210`, `turn_depth == 0`). The way back is **one** retry, no loop: `:1290-1305` — detects a tool
call in a fast response, restores `full_tools`, re-asks the same hop, warns with `retries`.

**Provable here.** `fast_path_tests` (:3078-3175) already asserts: small talk spoken takes it; the same
words typed do not; work words, a path, a snippet, a Windows path, 120 chars do not; 119 chars do; a
conversation that already used a tool keeps its tools; a non-chat request never takes it; the counter does
not move when read. **All unit-level and all green** — these are `fast_path_ok` tests, not turn tests.

**Not provable here.** That the retry actually restores capability end-to-end (a real model asking for a
tool on a fast hop, then completing on the retry), and that a small-talk turn is measurably faster. Both
need a model/provider.

**Findings while reading.**

- **V7 — the counter cannot be read by anyone who needs it.** `FAST_PATH_RETRIES` is a process-global
  `AtomicU64` (`:2353`) exposed only as `fast_path_misses()` — a Rust fn, no route, no log line except the
  `tracing::warn!` at :1293. The decision the commit itself sets up ("past roughly one turn in ten it is
  too loose") therefore needs a rebuild or a log digger to answer. Also global, not per agent or per
  language, so one chatty agent can drown the signal. Owner: data/Lead. This is a measurement gap, not a
  bug.
- **V8 — the 2.4 s in the commit message is a self-report.** [lap]. It is not in any artifact I can read.
  I will not repeat it as measured.

## F4 + T — the transcript, in the row and in the thread

**Landed.** `8b0e2cb` (row shows it), `17a3c4c` (thread adopts it), pinned by `a389470d`.

**What is true by code [QA].**
- Row: `session.ts:249-252` stores `frame.text` into `view.transcript`; `LiveVoiceRow.tsx:241-250` draws it
  in the middle slot when it is non-empty, with `title` for the full text.
- Thread: `LiveVoiceControl.tsx` adopts on each new transcript, once per utterance
  (`` `${topicId}-${heard.current.turns}` ``), through `adoptTurn` (`turns.ts:143-149`, store `update`, not
  `dispatch`) → reducer `adopt` (`frames.ts:388-398`) draws a stand-in `live-req-<id>`; the stored entry
  replaces it through `coveredByStored` (`frames.ts:456-478`), which matches a request by **content** or by
  timestamp within `STAND_IN_WINDOW_MS = 2000` (`:445-449`).

**Provable here.** `frames.test.ts:352-399` already asserts: drawn on first hearing; drawn once however
often the transcript repeats; gives way to the stored request (one entry, not two); phase and queue
untouched; appended below what was already on screen. All green in my run. This is the strongest item of
the four.

**Not provable here.** The whole point of T — that a person *sees* their words in the thread during a real
call — because the adoption path depends on a frame sequence only a server produces.

**Findings while reading.**

- **V9 — the row never goes back to the waveform.** `view.transcript` is written in exactly one place
  (`session.ts:250`) and cleared in exactly one place, `start()` (`:175`). Nothing clears it at the next
  utterance, at the end of a reply, or when the person starts speaking again. So from the first transcript
  of a session onward, the middle slot shows **that same text for the rest of the call** — the waveform
  never returns, and `view.level` would have nothing to drive anyway (`:373` sets it to 0 and nothing else
  writes it, already noted in `state-matrix.md`). Reproduction without a server: one transcript frame, then
  any number of state changes — the row still shows the text. This is a direct read, not a guess; it is
  also the kind of thing F4 was supposed to fix and half-fixed.
- **V10 — the adoption id resets on remount.** `heard.current.turns` is a `useRef` counter local to the
  mount, and the reducer refuses an id it already holds (`frames.ts:393`). Leave the conversation and come
  back mid-session, and the next utterance reuses `topicId-1`; the stand-in is skipped, so the thread shows
  nothing for it until a history read. Needs a React mount to prove — no jsdom in this package — so it is a
  hypothesis with a line number, not a finding yet.
- **V11 — a clock skew can leave a duplicate.** A stand-in is covered by content **or** by being stamped
  within 2 s of the stored request. The stand-in is stamped by the browser (`new Date()`), the stored one by
  the server. If the two clocks differ by more than 2 s and the stored text is normalised (punctuation,
  casing, a recognised fill-word dropped), the stand-in is never covered and the thread shows the utterance
  twice until a reload. Needs a server, two clocks and a provider — exactly the class of defect that will not
  show up in any test written today.
