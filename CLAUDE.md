# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Vizier is a Rust-based AI agent framework, a workspace of four crates (see **Workspace layout**): the engine as a library (`vizier-core`) and, on top of it, a single binary that runs multiple concurrent AI agents, each with its own tools, memory, and provider, exposed over Discord, Telegram, and HTTP (REST + WebSocket + a bundled React WebUI). Storage is embedded SQLite — no external DB service required. Agent memory itself lives as human-readable markdown documents on disk (organized into per-agent **bundles**, see below), read/written through a pluggable `DocumentStore` abstraction; every other entity lives in SQLite.

## Workspace layout

A virtual Cargo workspace (`members = ["crates/*"]`, `default-members = ["crates/vizier"]`, so a bare `cargo run`/`cargo build` is the server). Every version string lives in the root `Cargo.toml` (`[workspace.package]` and `[workspace.dependencies]`); a release edits that one file. Dependencies point **one way**:

| Crate | Path | Holds |
|---|---|---|
| `vizier-derive` | `crates/vizier-derive/` | derive macros |
| `vizier-core` | `crates/vizier-core/` | the engine: agents, tools, storage, providers, scheduler, `VizierRuntime`, Discord/Telegram readers. No web framework, CLI or terminal UI (the `policy` CI job checks each crate's *direct* dependencies). Feature flags `channel-discord channel-telegram provider-media addon-docker addon-documents utoipa telemetry` (`full` = all, `default = []`; naming scheme and the flag→dependency table in `docs/src/configuration/build-flavours.md`) |
| `vizier-http` | `crates/vizier-http/` | the axum REST/WebSocket server, JWT/argon2 auth, OpenAPI, the embedded WebUI and integration icons; `serve(&runtime, config)` and `router(..)` |
| `vizier-schema` | `crates/vizier-schema/` | the Fleet bus contract (#162): validated `Subject`/`SubjectPattern`, a versioned `Envelope` (1 MiB payload limit), the `Messaging`/`Leases`/`SharedState` traits bundled in `Bus` with `Capabilities`, the `InProcess` backend, a backend conformance suite (`conformance::run`), `RoleContract` skeletons and `testing::ScriptedPeer`. **A leaf**: it depends on no workspace crate, broker, web or CLI crate (the `policy` job checks). Docs: `docs/src/fleet/bus-contract.md` |
| `vizier-fleet` | `crates/vizier-fleet/` | the Fleet roles (epic #159): one struct per role (`gateway-http`, `gateway-grpc`, `worker`, `channels`, `control`) built from the **bus** (first parameter), the config and the storage traits only, each with `needs()` (the bus capabilities it requires; `vizier run` refuses a backend that lacks one), plus `pending(role)` → the sub-issue that wires it. Still skeletons (no behaviour until #166–#170); `testing::Harness` builds one role alone on an in-process bus with embedded storage. Roles never import each other (the `policy` job checks) |
| `vizier` | `crates/vizier/` | the binary: clap CLI, `--role`, onboarding, the command socket, config-file/workspace resolution, logging and OTLP export, exit codes. Its own `role-*` features (`default = ["role-all"]`) decide which Fleet roles it carries |
| `vizier-app` | `app/src-tauri/` | the desktop app (spec 038): a Tauri 2 shell that hosts a `VizierRuntime` in-process and serves the WebUI in a window. **Its own Cargo workspace** (`app/Cargo.toml`, own `app/Cargo.lock`, `publish = false`), not a member of the root workspace, so `cargo build --workspace` never needs webkit; its version is bumped with the root one by the release job. Native-code dependency versions must match the root lockfile (CI `policy`) |

`vizier-core` has two public tiers: the stable one (`VizierRuntime`, `config`, `schema`, `auth`, `error`, `transport`, `access`) and a `#[doc(hidden)]` adapter surface that `vizier-http` and `vizier` reach into until the application-service layer replaces it (#102). New engine code goes in `vizier-core`; a new route in `vizier-http`; a new CLI flag in `vizier`. Core never reads `$HOME`, `$VIZIER_CONFIG` or `$VIZIER_DATA_DIR` to decide where data lives and never exits the process: `VizierRuntime::start` takes an explicit workspace and reports a stopped subsystem through `wait`/`events`/`health`, and takes `{workspace}/.runtime/vizier.lock` so a second engine on one workspace is refused. See `specs/037-core-extraction/` and `crates/vizier-core/examples/headless.rs`.

## Commands

```sh
just install     # submodules, npm i in design/ and webui/, cargo fetch
just dev          # cargo watch -s "just run" (hot-reload)
just run          # cargo run -- run --config dev.vizier.yaml
just run-d        # same, detached (-d)
just shutdown     # cargo run -- shutdown --config dev.vizier.yaml
just build        # cd webui && npm run build
just landing      # the website (landing, blog, docs) on http://localhost:4321
just landing-build # build the website
just release      # cargo build --release
just app-dev      # the desktop app with hot reload (cd app && cargo tauri dev)
just app-build    # build the WebUI, then the desktop bundles (cd app && cargo tauri build)
just app-test     # cd app && cargo test
just catalogue-update  # refresh crates/vizier-core/assets/catalogue/ (models.dev seed + logos) — needs network
just test-scripts  # node --test for scripts/*.mjs
just jaeger       # local Jaeger in Docker (UI :16686, OTLP :4318); jaeger-down removes it
just run-otel     # just run, exporting traces to that Jaeger with content capture on (dev-otel: hot reload)
just docker       # docker-compose down && docker-compose up -d

cargo test --workspace     # run tests (see below)
cargo clippy --workspace   # lint
cargo test -p vizier-core --no-default-features   # the engine with no optional features
cargo test -p vizier-core --no-default-features --features <flag>   # one flag alone, as CI does (channel-discord, addon-docker, …)
cargo test -p vizier --no-default-features --features role-worker   # one role alone, as CI does (role-gateway-http, …)
```

CI is path-aware (`.github/workflows/ci.yml`): a PR runs the jobs of the crates and flags it touches and the `gate` job is the one required status; `develop`, `master` and release tags run every flag alone, and every `role-*` of the binary alone. A new flag needs an entry in the `changes` job (paths) and the flag list there, and must be listed in `full` (the `policy` job checks); a new role needs an entry in the same `changes` job and in `role-all` (the `policy` job checks `role-all` lists exactly the `role-*` flags).

`just test` and `just lint` run the workspace-wide versions of the two above. Tests are sparse (`crates/vizier-core/src/agents/agent/model/registry.rs`, `crates/vizier-core/src/storage/memory.rs`, `crates/vizier-core/src/skill/context.rs`); most correctness is exercised by running the binary, not by a test suite. For end-to-end checks, run the binary with an agent on the offline `dummyplug` provider (no keys needed): send `tools`, then a tool name for a sample request, then the JSON request to run the tool through the real loop (and `context` to echo the per-request context block the agent received, §6) — see `specs/008-dummyplug-provider/contracts/dummyplug-protocol.md`. The constitution requires this for any agent-observable change.

WebUI typecheck: `cd webui && npm run typecheck` (runs `react-router typegen && tsc`).

### Build gotcha: `crates/vizier-http/build.rs` runs the WebUI build

`webui/` and `design/` are git submodules (`vizier-lab/webui`, `vizier-lab/design`); `legacy/` is the previous WebUI, kept for reference and never built, served or packaged. `crates/vizier-http/build.rs` shells out to `npm run build` in `webui/` on every build of `vizier-http` (so of the server) **if** `webui/node_modules/` exists, then stages `webui/build/client/` (or, in a published crate, the packaged `webui-dist/`) into `$OUT_DIR/webui`, which `rust-embed` embeds. If neither exists, the build panics. `vizier-core` builds without the WebUI. Run `just install` (it initialises the submodules) first, or make sure `webui/build/client/` is pre-populated (this is how crates.io publishes work — see `include` in `Cargo.toml`).

## CLI subcommands

- `vizier run [-c <path>] [-d] [--port] [--workspace/--data-dir] [--storage sqlite] [--workers] [--ws-idle-timeout] [--role <role>[,<role>]]` — start agents, scheduler, channels, and the command server. `--role` (or `VIZIER_ROLE`) selects server roles: `all` is the default and the only one that runs until #166–#170 land, and any other is refused with the sub-issue that wires it in (`vizier_fleet::pending`). Works with **no config file** (config-less mode, see below). `sqlite` is the only supported `--storage` value; a deployment still configured with the legacy `filesystem` backend is migrated into sqlite automatically on first startup after upgrading (see `dependencies.rs`'s migrations below) — `--storage filesystem`/`VIZIER_STORAGE=filesystem` on a *new* invocation is rejected outright.
- `vizier shutdown [-c <path>]`
- `vizier onboard -p <path>` — interactive wizard that writes a seed `.vizier.yaml`.
- `vizier skill install|list|uninstall|update`
- `vizier agent ps` — list running agents. Agents themselves are created/managed at runtime via the WebUI or HTTP API — there's no `agent create` CLI.

### Config-less mode

Resolution order for the config file: explicit `-c` → `$VIZIER_CONFIG` → `./.vizier.yaml` → built-in defaults. In the no-file path, the workspace resolves to `$VIZIER_DATA_DIR` or `$HOME/.vizier`, and storage defaults to `sqlite`.

## Architecture

### Process startup (`crates/vizier/src/cli/server.rs::run_server`, `crates/vizier-core/src/runtime.rs`)

`run_server` builds the tokio multi-thread runtime and starts a `VizierRuntime`, which spawns four long-lived tasks off one shared `VizierDependencies`: `AgentHost`, `VizierScheduler`, `ChannelReaders` (the Discord/Telegram readers) and the deps' own command handler (`VizierTransport::run`). The binary adds two of its own, `vizier_http::serve` (only when the `gateway-http` role is selected) and `VizierCommandServer` (which also answers `CommandRequest::Roles` locally, for `vizier agent ps`). **Fleet (#161):** `RuntimeOptions.roles` (`ServerRoleSet`) decides which of the four the runtime spawns — the command handler always — and `RuntimeOptions.gate` (`runtime::Gate`; `None` = `AlwaysYes`) is asked by the scheduler before `recover`, on every tick and before a dream command, and by `ChannelConnections::reconcile` (a closed gate wants no readers, so it stops the ones it runs). Each runs for the life of the process, so if any one stops (error, panic or return) the runtime reports it and `run_server` logs it and **exits with code 1** for Docker/systemd to restart vizier whole, rather than run half-working (#51); a requested exit (`vizier shutdown`) is code 0. A subsystem's `run` must therefore never return while things are healthy (`ChannelReaders::run` waits on its watcher forever for this reason). The runtime itself never exits the process. The one tolerated failure is a command socket that can't be bound: it is logged and vizier runs on without `vizier shutdown`/`agent ps`. They all communicate through `VizierTransport` (`crates/vizier-core/src/transport/`), which runs on the **Fleet bus** of `vizier-schema` (`transport.bus()`; `InProcess` today). **Fleet bus (#162):** `agent.{id}.req` carries a turn's request (`wire.rs`: the request plus the fields `VizierRequest` keeps out of serde — `transient`, the client binding — with the trace as `traceparent`/`tracestate` headers and `x-vizier-turn-id`/`x-vizier-resumed`); an agent reads it from a cloneable `Inbox` (`register_agent`; the receiver is still handed from supervisor to supervisor across updates), and replies stream over `reply.{uuid}` — `transport.reply_channel().await` gives a `(ResponseSender, ResponseStream)` that keep the old flume method names, the stream subscribes before anything can publish, a frame over 1 MiB is cut (message text) or dropped with a warning, and the sender publishes an end frame when its last clone drops (that close is how requesters learn an agent stopped). Agent lifecycle commands (`agents.cmd`), memory ops (`agent.{id}.memop`), dream commands (`dream.cmd`), file commands (`files.cmd`) and the command socket (`process.cmd`) are bus requests; `AgentCommand` still carries an in-process answer slot, but it is stripped before the bus and refilled from the reply. **File bytes never ride the bus**: the sender stages them in the blob store under `staging/{uuid}` (`VizierTransport::with_blobs`) and sends the key. Each serving end subscribes in its constructor (`AgentHost::new`, `VizierScheduler::new`, `serve_file_commands`) so nothing sent after startup is missed. **Process-local on purpose:** `exit_channel`/`exit_signal` (this process's lifecycle) and a client tool's live socket (`ClientConnections` on `VizierDependencies` resolves a `ClientBinding`'s `connection_id`; a miss reads as closed). There's no shared mutable state beyond what's routed through this transport plus the shared `VizierStorage`. It also carries session events (`transport/events.rs`: `publish_session_event` / `subscribe_session_events` keep their signatures and the `broadcast` lag behaviour, with one pump task publishing to `session.{id}.events` and `integration.changed` and fanning `session.>` back into the local broadcasts; an event that cannot go on the bus is delivered locally) — `SessionEvent { session, frame: SessionFrame::{Response, Job} }`: things pushed to whoever watches a session — background job changes, reactions, the frames of a turn a background report woke, and the frames of every WebUI turn. WebUI sockets subscribe (each filtering on its own session) and the WebSocket handler publishes a person's turn there rather than writing it to the socket that sent it, so a page reopened mid-turn, or a second tab, still receives the rest of it. The Discord/Telegram readers subscribe too, for the woken turns of their own channels (`channels/woken.rs`); their own people's turns still stream through a per-message forwarder.

### Desktop app and the service layer (`app/`, `crates/vizier-core/src/service/`, `crates/vizier-http/src/{embedded,topic,error}.rs`; `specs/038-desktop-app-edition/`)

The desktop app is a second **host** of `VizierRuntime` beside `run_server`: `app/src-tauri/src/engine.rs` starts the runtime on a workspace, resolves the signed-in person (`DesktopState`: starting, locked, needs_owner, choose_owner, ready, degraded, failed) and emits `desktop://state`. A workspace locked by another process is the `locked` state, from `{workspace}/.runtime/vizier.lock`. The app opens **no port** by default; opt-in web access (`web_access.rs`) runs `vizier_http::serve` bound to `127.0.0.1` (or all interfaces on request) with a key in `{workspace}/.runtime/web-access.key`, a CORS allow-list of its own origin, and refuses to turn on until the owner has a password (the owner is created with one; an owner from an older workspace may have none).

- **Identity.** `auth::Identity` is now `auth::Principal` and `AuthMethod` gained `Desktop` (recorded like a WebUI action). `Services::principal_for` refuses to mint a `Desktop` principal; only `embedded::Dispatcher` can. `AuthMode::{Network, Desktop{user_id}}` on `HTTPState` makes `require_auth` resolve that one user on every request (role and permissions re-read, so revocation is immediate); in `Network` mode a request that already carries a `Desktop` principal is refused. `tests/desktop_principal.rs` pins that no network path yields it (SC-010).
- **Service layer.** `vizier_core::service` (`Services`, `ServiceError`) is where operations and their authorization live; `ServiceError` kinds map one to one onto the HTTP envelope in `vizier-http/src/error.rs`. Permission helpers (`can_view_agent`, `can_edit_agent`, `can_show_platform_chats`, `require`) are in `access.rs`; argon2 is in `auth/password.rs` (`has_password`, `GET /auth/users/me` returns `has_password`). Handlers are being moved onto it domain by domain; **new authorization goes in core, not in a handler**. `tests/conformance/` (one `groups/*.rs` file per route group) sends every vector through the network router and the dispatcher as three fixture users and compares with `target/038-baseline/conformance/` (`CONFORMANCE_RECORD=1` records); `tests/conformance/pending.txt` lists the OpenAPI routes still without a vector and may only shrink.
- **Dispatcher and topics.** `embedded::Dispatcher::dispatch` runs an `http::Request` through a private router (no WebUI fallback; it never hands out the router or state, pinned by a `compile_fail` doctest). A chat socket is a `topic::TopicConnection` (`open`, `handle_inbound(frame)`, `outbound().run()`, `close`) that the WebSocket handler and the app's IPC both drive; frames are `serde_json::Value`.
- **IPC.** The WebUI talks to the app through four paths (contracts/ipc-protocol.md): the `api` command (method, path, body in, `{status, body}` out), the `vizier-asset://` scheme for streamed and ranged files, `topic_open`/`topic_send`/`topic_close` over a Tauri `Channel`, and `desktop_*` commands plus `desktop://` events.
- **WebUI transport seam.** `webui/app/api/transport/` (`index.ts` picks `http.ts` or `tauri.ts` once; `await transportReady`) is the only code allowed to call `fetch`, open a WebSocket, build `/api/v1` URLs or import `@tauri-apps/*`; `boundary.test.ts` fails otherwise. `client.ts` and `socket.ts` are thin delegates. In desktop mode there is no login, no token and no Sign out.
- **Releases.** `release.yml` has a `build-app` matrix (universal macOS `.dmg`, x86_64 and arm64 AppImages), checks the architectures, signs the updater payloads with `TAURI_SIGNING_PRIVATE_KEY`, and `scripts/app-latest-json.mjs` writes `latest.json` (`tauri-plugin-updater` reads `releases/latest/download/latest.json`). macOS is unsigned until #132 (the release notes say how to Open Anyway). The server's four tarballs are untouched.
- **Windows** (`specs/039-windows-app-support/`, the app only; the server stays Linux/macOS/Docker). `build-app` has a `windows-x64` leg that ships the per-user NSIS installer `Vizier_<version>_x64-setup.exe` (+ `.sig`, `.sha256`; MSI is out because it rejects `-rc.1` versions) and a `windows-x86_64` entry in `latest.json`; `ci.yml`'s `app` job compiles on Windows too. The installer is unsigned like macOS (#132). `app/.cargo/config.toml` passes `/MD` to `cc` because `esaxx-rs` hard-codes `/MT` and the linker refuses to mix runtimes with whisper.cpp/onnxruntime (LNK2038). A local agent shell on Windows is PowerShell (`LocalShell`; the `shell_exec` description says so), `.sh` skill resources return a clear error, and the local blob store refuses names Windows cannot hold (`windows_segment_problem`). The WebUI asks `convertFileSrc` for the `vizier-asset` base (WebView2 serves it as `http://vizier-asset.localhost`). On Windows `just` runs recipes through PowerShell: only `install-app`, `app-dev`, `app-build` and `app-test` are supported there, and the system prerequisites (MSVC Build Tools, CMake, LLVM + `LIBCLANG_PATH`, WebView2) are documented in the README, not scripted. Smart App Control blocks cargo's build scripts (error 4551) until it is turned off.

### `VizierDependencies` (`crates/vizier-core/src/dependencies.rs`)

Constructed once at startup: opens the configured SQL backend (`sqlite` by default, or PostgreSQL with pgvector) and file backend (`local` by default, or S3-compatible object storage), then runs one-time legacy migrations only on SQLite (seed users → superadmin role, YAML providers → provider storage, per-agent MCP/shell config backfill, legacy identity backfill — itself due for removal before 1.0.0, #82). It owns the shared `SqlStore` and `BlobStore` used by every subsystem and is cloned cheaply (`Arc` internals).

### Agents (`crates/vizier-core/src/agents/`)

### The agent seam (`crates/vizier-core/src/agents_client.rs`)

- `AgentsClient` is **the one way the gateway side reaches an agent** (#163). `core::service` and `vizier-http` call it; they never read a running agent's memory. It is held as `Arc<dyn AgentsClient>` on `VizierDependencies.agents`, so a test can put a fake there without touching the engine. Nine operations, all returning `crate::Result`: `request`, `abort`, `create`, `update`, `delete`, `restart`, `health`, `integration_status`, `refresh_integrations`. The contract is written down in `specs/048-agent-service-seam/contracts/agents-client.md` so a networked implementation (#168/#169) can be built from it alone.
- Every operation addresses the **agent**, never a host, a node or a lease: a turn travels on `agent.{id}.req`, a lifecycle command on `agent.{id}.cmd` (one subject per agent, so only its owner answers it), and a create on the fleet-wide `agents.cmd`. An abort is the request that aborts a turn today (`Command("abort")`), not a new message kind.
- `LocalAgentsClient` reaches the manager **over the bus**, so the local path is the path a networked one takes. `FakeAgentsClient` records what it was asked and answers from a script, so the gateway side is testable with **no agent host running** (`vizier-http/tests/agents_seam.rs`).
- **Two availability reasons, one kind.** An agent that cannot be reached fails with `ErrorKind::AgentUnavailable` - the kind the WebUI and the channels read today - and the reason rides in the message: *no owner* (the bus answered `NoResponders`, so it fails at once) or *owner lost* (the bus answered `Timeout`, so the request ends within its deadline and never hangs). `AgentUnavailable::parse` reads the reason back.
- **The published views** (`agents/views.rs`) are what a gateway reads when it cannot ask the owner: `agent.{id}.health` and `agent.{id}.setup`, written to shared state by the host (on take, on every state change, and refreshed) and by the setup board. The value is `{"expires_at_ms", "data"}` - the deadline is **in the value**, because `SharedState` has no TTL - and a missing or expired entry reads as **unknown**, never as a stale value. `scripts/048-agent-state-read-check.sh` refuses a new direct read of a running agent's state and names the file and line; the audited exceptions are in `specs/048-agent-service-seam/contracts/agent-state-audit.md`.
- **Placement** (`agents/placement.rs`) decides which host owns which agent; in one node `SingleNodePlacement` returns every stored agent for the one local host, so a single node behaves exactly as before.

- `AgentHost` (`crates/vizier-core/src/agents/mod.rs`) is the manager: on boot it registers the request channel of every agent **it was told to hold** (`Placement` decides which; in one node that is every stored agent, so nothing changes - #163) and spawns a `Supervisor` (`crates/vizier-core/src/agents/supervisor.rs`) per agent, then services `AgentCommand::Create/Update/Delete/HealthCheck`. Registration comes before anything is built, and the channel's receiver passes from supervisor to supervisor across updates, so requests sent while an agent starts or restarts queue instead of failing with "not registered" (this is also why `run.rs` builds `AgentHost` before the scheduler). The supervisor builds the agent (`BuiltAgent::build`: Ollama pull, indexer, `VizierAgent::new`), runs `agent_process` in its own task so a panic ends the run and not the supervisor, and on a failed build or run records `Failed { last_error, failures, next_retry_at }` (visible through `HealthCheck`, `GET /agents/health` and `vizier agent ps`) and retries with backoff (2s doubling to 5m), answering requests with `ErrorKind::AgentUnavailable` meanwhile. Every stored agent has a supervisor whatever its state, so update and delete always work. Create and update **build before they persist or swap**: a config that can't start is refused and an updated agent keeps running on its previous config. The build runs as its own task off the command loop (`AgentHost.builds`), so a slow one (an Ollama pull) never delays other agents' commands or health checks; while an agent has a build in flight, other creates/updates/deletes of it are refused as busy. When an agent instance stops (update, delete, restart) its running turns are **aborted**, not detached. An update or restart then **resumes** them on the next instance (open tool calls sealed with a stop notice, the original sender kept, no `AgentUnavailable`); a delete drops them and their senders get an `AgentUnavailable` error. Requests still queued behind them are re-sent on the agent's channel for the next instance, or rejected if the agent was deleted (#52).
- `VizierAgent` (`crates/vizier-core/src/agents/agent/mod.rs`) is the actual per-agent loop: builds its `VizierModel` (provider abstraction), `VizierTools`, `VizierSkills`, optional STT/TTS/image-gen, reads its identity memory (`core/soul`) fresh each turn and loads its owner profile, and runs the LLM request/response/tool-call cycle (`agents/process.rs` drives it against `VizierTransport`'s per-agent channel).
- Each agent owns its **own** MCP client set and shell instance: the shell is built from its `AgentToolsConfig` in `BaseTools::new()`, the MCP clients from the MCP integrations attached to it (see Integrations below), never shared between agents even when the definition is. There are no global MCP/shell singletons — this is deliberate (per-agent isolation). Each MCP server is an `McpServer` (`agents/mcp/`) that connects in the background, caches its tool list (5 min TTL, or until `tools/list_changed`), bounds connects and listings by timeouts, and reconnects with backoff after a crash or hang; a server that's down only drops its own tools from the turn, never fails it.
- `hook/` — lifecycle hooks (debug logging, thinking-block handling, tool-call handling, handover).
- `shell/` — local and Docker (`bollard`) shell execution backends behind one abstraction.
- **User-invoked skills** (`specs/021-user-invokable-skills/`): `/<skill> [input]`, `/skill <name> [input]` and `/skills` arrive from every channel as plain `Chat` text and are told apart once, in the `Chat` arm of `agents/process.rs`, by the pure `skill::invocation::parse` (resolution: `invocation::resolve`, agent skill before global, case-insensitive, `_` = `-`). A resolved skill is passed to `VizierAgent::chat` as `Invoked`; its content goes into an `## Invoked Skill` section of `context_md` (never a system prompt) and the model's message is the input, while history keeps the typed text plus `metadata.invoked_skill`. `/skills` and unknown names are answered by `answer_directly` with no model call. Discord registers each skill as a slash command (plus `/skill` with autocomplete) and Telegram sets its `setMyCommands` menu, both through `channels/commands.rs` (`build` per `PlatformRules`, `CommandSync` + `watch` re-checking every 60 s and sending only on change); a Discord skill command is turned back into the same `Chat` text. Telegram lets an unmentioned group message through only when it names one of the agent's skills.
- **Side chats** (`specs/033-btw-side-chat/`): `/btw` is `VizierRequestContent::Btw(SideChat { question, turns })`, always `transient`, built only by `channels/side_chat.rs::ask` (validates 4,000 characters per question and 32,000 per side chat, takes a hit on `deps.side_chat_limits`, 5 per 60 s per platform identity, then awaits the first reply under `prompt_timeout`). `agent_process` routes it to `run_btw` beside `checkpoint`/`lobotomy`, never to `chat` or `handle_request`, and `records_session_activity` (false only for side chats) skips the `refresh_session_detail` spawn and both `update_thinking_state` calls. **That gate is the no-trace guarantee**, pinned by `btw_tests`: a new per-request write in `agent_process` must be gated on it. `VizierAgent::side_chat` rebuilds a host turn's prompt prefix (system prompts, checkpoint handover, history since the checkpoint) plus the aside's turns and makes one tool-less `complete_until`; a tool call is dropped, and `SIDE_CHAT_NO_TOOLS` answers when no text is left. It saves nothing and returns no `history_uid`, so usage is the only trace. HTTP is `POST /agents/{id}/btw`. Discord and Telegram keep live asides in `SideChats<P>` (memory only) and share `classify_reply`; each reader recognises replies to an aside's messages at the very top of its message handler, before `/abort`, attachments and `Chat`/`SilentRead`. Discord asides are public (`SIDE_CHAT_MARKER` on every chunk, forgotten after 5 min idle, the messages stay); Telegram deletes them after 2 min through the content-free ledger `side_chat_pending__{agent_id}` in `state` (`telegram/side_chat_ledger.rs`: ids and a deadline only; a 15 s tick deletes what is due, so a restart still deletes).
- `skill/` — reusable agent behaviors, separate from the top-level `skill/` module (skill *packages*, install/registry).

### Artifacts and session files (`crates/vizier-core/src/artifacts/`, `crates/vizier-core/src/session_files/`)

Files come in two tiers. **Session files** are transient conversation uploads under
`<workspace>/uploads/<file_id>/`, in the `session_file` table. **Artifacts** are permanent,
agent-owned files under `<workspace>/artifacts/<agent_id>/<artifact_id>/content.v<n>`, with
metadata/events/references in SQLite (`ArtifactStorage`).

- `Artifacts` (`crates/vizier-core/src/artifacts/mod.rs`) is the one service: promote (copies the bytes; the source
  is untouched), replace (writes `content.v<n+1>` then switches the row, removes the old file),
  list/detail/activity, delete, and the sync `AttachmentResolver` that turns
  `VizierAttachmentContent::Artifact { agent_id, artifact_id }` into current bytes for
  `to_part`, `to_tool_result` and `FileManager::resolve`.
- `SessionFiles` is the one clear/delete service used by the WebUI side panel, `/clear-files`
  (`/clear_files` on Telegram), conversation deletion and agent deletion. Refuses while a turn is
  running/queued; deletes records first, then an `uploads/<file_id>/` blob only when its
  reference count is zero (`json_extract`). **No automatic GC or retention.**
- Deletion is reference-only both ways: deleting a conversation/memory keeps the artifact;
  deleting an artifact keeps message/memory bodies (messages read `available: false`, memory
  links are removed with a revision).
- Four permissions: `all_agents`/`owned_agents` × `view_artifacts`/`manage_artifacts`
  (`crates/vizier-core/src/artifacts/access.rs`; `manage` implies `view`, system bypasses). Reads use view,
  promote/delete use manage.
- `artifact_reference` is a derived index written with history saves and memory writes, and
  reconciled at agent start — never scan history JSON or memory documents at gallery read time.
- `MemoryAttachment` is a two-variant enum (`Artifact { artifact_id, name }` |
  `LegacySessionFile(VizierAttachment)`). `memory_write` is content-only and preserves existing
  attachments; attach/detach are separate tools/API operations that rewrite only frontmatter, the
  node, a revision and reference rows. Legacy session-file memory attachments and legacy
  `Local`/`Url`/`Bytes`/`Base64` message attachments are read-only compatibility tracked in #82.
- Dreams may read their source conversations' session files and promote/list/attach/detach
  artifacts (`ToolContext.dream_sources`); they cannot update/delete artifacts, send attachments,
  load one into a session, or clear files.

### Tools (`crates/vizier-core/src/agents/tools/mod.rs`)

Tools implement the `VizierTool` trait: associated `Input`/`Output` types (both `JsonSchema + Serialize + Deserialize`), `name()`, `category()`, `description()`, `call()`. `category()` is required and returns `Option<ToolCategory>`, one of 15 variants in display order: `Memory, Identity, Scheduling, Agents, Skills, Files, Scratchpad, Web, Audio, Media, Discord, Telegram, Webui, Shell, Integrations`. Only the four direct tools and the two dream-journal tools return `None`; `every_tool_is_in_its_category` in `tools/mod.rs` pins the full table.

**Memory tool names** (`tools/vector_memory/`): `memory_search` searches and returns addressed **passages** (it was `memory_read`), and `memory_read` returns one whole document by `(bundle, path)` (it was `memory_detail`; `memory_detail` is retired, not aliased). The two renames are a breaking change and landed together, because tool names are the dispatch key. The other six `memory_*` tools are untouched. A blanket impl turns any `VizierTool` into the dynamic `VizierToolDyn` used for dispatch. Two built-in toolsets exist per agent — `default_toolset` (always-on: memory — including Core, which *is* a memory at `core/soul` — scheduler — including `list_task_runs`/`get_task_run_detail` for an agent's own task results — skills, subtasks, session files, consult/delegate other agents) and `user_toolset` (conditionally added per agent config: fetch, http client, TTS/STT/image-gen, webui messaging). Both live in `BaseTools`, built once per instance. Integration tools (Discord/Telegram, addons, MCP) come from `IntegrationKind::contribute` into an `IntegrationTools` layer; `tools::compose(&BaseTools, Arc<IntegrationTools>)` builds the `ToolRouter`, `sandbox_toolset` and `categories`, and `VizierAgent` holds the result in an `ArcSwap<VizierTools>`. A turn loads one snapshot at entry and keeps it (system prompt and every tool call); `refresh_integrations()` swaps in a new one for the next turn, reusing unchanged contributions (and their `McpServer` connections). **Addon tools are namespaced** `<addon id>_<tool>` and listed under the addon id as category (Brave: `brave_search_web`, `brave_search_news`, category `brave_search`; the old `web_search`/`news_search` names are gone, not aliased); addon ids are reserved category names, so an MCP server named `brave_search` gets `brave_search_mcp`. MCP tools are named `<server>_<tool>` (sanitised by `python_identifier`), with the server key as their category, or `<key>_mcp` when the key is a built-in category's name. `ToolRouter::catalogue()` is the single source for naming, categories and dispatch: native names are reserved first, MCP names are assigned in `(server, tool)` order, and a taken name gets `_2`, `_3`, …. The old `mcp_<server>__<tool>`, `READ_CORE` and `WRITE_CORE` names are not supported anywhere, and neither are `read_core`/`write_core`: identity is the memory document `core/soul`, read and written with `memory_read`/`memory_write` (specs/043-unify-core-and-memory).

**Secrets** (`specs/027-agent-secrets/`): `set_secret`/`get_secret` (`tools/secrets.rs`, category `secrets`, the 16th built-in category; `questions` is the 17th, spec 042; `time` is the 18th and last, spec 052; `identity` left the list in spec 043) let an agent store and retrieve credentials from its own store (`agent_secret`, `agent_secret_event` in SQLite behind `SecretStorage`; `crates/vizier-core/src/secrets/` holds validation, access and the service facade). A value is script-only: `get_secret` returns it to the Python script, while the turn's `SecretRedactor` (`ToolContext.secret_redactor`) scrubs it from the report (`result`, `stdout`, traceback, nested call arguments/error), from `execute_tool` telemetry and from `DebugHook` output as `[redacted]`. The set input is explicitly outside that guarantee (the script carries the value). Neither tool is in `DREAM_TOOL_NAMES`, and `secrets` is a reserved category name (an MCP server keyed `secrets` becomes `secrets_mcp`). People manage the store over `/agents/{id}/secrets` (list/put/delete/events; no response carries a value) under `all_agents:secret` or `owned_agents:secret` (ownership) — see `crates/vizier-core/src/secrets/access.rs`, the WebUI Secrets page and `docs/src/configuration/secrets.md`. Deleting an agent deletes its secrets and events.

**Code mode** (`specs/007-code-mode-python-sandbox/`, `specs/014-tool-categories-code-mode/`): every agent is always in code mode; there is no `tools.python` config and no `ToolExposure`. The model is offered only `sandbox_toolset` (`think`, `execute_python`, `list_tool_functions`, `describe_tool_function`), and `VizierTools::call` refuses any other name. Every other tool is reached from scripts through `ToolRouter` (`VizierTools.router`). `VizierTools.categories` (built once from registered tools and configured MCP server keys, never live listings) feeds the `SANDBOX.md` system prompt, which lists the categories and stays byte-identical across turns; `list_tool_functions {category?}` and the in-script `list_tools(category=…)` list one category (an unknown one is `did_you_mean` data, or a catchable `ValueError` in a script). The tools are in `crates/vizier-core/src/agents/tools/python/` (`execute_python`, `list_tool_functions`, `describe_tool_function`, plus `RouterBridge`, which runs script-made tool calls through `ToolRouter` + `ToolContext.hooks` + the per-tool timeout). The engine is `crates/vizier-core/src/sandbox/`, which is agent-agnostic: a monty resume loop on `spawn_blocking`, the `SandboxBridge` trait, JSON⇄`MontyObject` conversion, and `ToolFunctionDoc` built from `ToolDefinition` (`llm::types::ToolDefinition`). Script failures come back as an `ExecutionReport` (data), never `Err`. The sandbox tools are never in `DREAM_TOOL_NAMES`; `dream_tools`/`dream_call` bypass `sandbox_toolset` and call the router directly.

**Durable turns** (`specs/023-persist-turn-activity/`): every request `VizierRequest::is_durable` accepts (not `abort`/`dream`, not a dream session) is journaled by `VizierTransport::send_request` as a `session_turn` row (`TurnStorage`, `storage/turn.rs`; transport built with `VizierTransport::durable(storage)`), `queued` → `running` (`start_session_job`) → deleted when the turn ends (`join_next`) or on `/abort`. Steps are saved **as they happen** (`agents/steps.rs`: `StepRecorder`, `record_step`) and pushed as `SessionFrame::HistoryEntry` (`history_entry` on the socket); the WebUI builds the running trail from history merged by uid, not from the live `thinking`/`tool_choice` frames. A call a stop cut off gets a result from `seal_open_calls` with a `StopReason` notice (`Stopped:`/`Interrupted:` prefix) on abort, panic, instance stop and resume, so history never holds a call without a result. At startup `AgentHost::resend_pending_turns` re-sends each agent's rows in order; a `running` row is sent `resumed`, and `chat_turn` resumes it from its last step (`split_at_request`, `prompt_with`'s `progress`) and marks the reply `VizierResponse.resumed`. `note_resume` + `MAX_RESUMES_WITHOUT_PROGRESS` give up on a turn that keeps bringing vizier down. Startup keeps scratch files and the thinking mark of sessions with a row.

**Scratchpad** (`specs/020-scratchpad-tools/`): `write_tmp`, `append_tmp` and `read_tmp` (`tools/scratchpad.rs`, category `scratchpad`, on `default_toolset`) keep named plain-text files private to one conversation, in the `scratch_file` table behind `ScratchStorage` (`storage/scratch.rs`), keyed `(agent_id, channel slug, topic or '', name)`. Limits (1 MiB per file, 64 files, a safe name rule) are checked in one storage transaction, and every refusal or miss is a `status` result, never `Err`. A conversation's files last while it has a turn running or queued: `agents/process.rs` clears them (awaited inline, so no turn can start in between) when a session goes idle, on `/abort`, and on instance stop for sessions with an empty queue (a handed-on queue keeps them). `dependencies.rs` clears every row at startup (except sessions with a pending `session_turn` row), and `delete_session`/`delete_agent` delete theirs. The three names are in `DREAM_TOOL_NAMES`; each dream stage is its own session, so its own scratchpad. `scratchpad` is a reserved category name (an MCP server keyed `scratchpad` becomes `scratchpad_mcp`).

**Background jobs** (`specs/012-background-subagent-results/`): `background_subagents` is **non-blocking and reports back** (`delegate_agent` was removed in spec 053 for `mention_agent`; saved delegation jobs and `InterAgent` history still read, tracked on #82). `parallel_subagents` is the blocking counterpart: it creates no job, waits in the current turn under `ToolContext.deadline`, and dispatches transient pieces that a dropped turn aborts. The background tools are thin wrappers over `BackgroundJobs::launch` (`crates/vizier-core/src/agents/background/`, held on `VizierDependencies.background_jobs`), which records the job, sends each piece to its own session (`Subagent` for a batch, `InterAgent([origin, target])` for a delegation, always with a fresh topic), and leaves a runner awaiting them under a per-piece time limit (`timeout_secs`, default 600, max 3600; a timed-out piece gets the existing `abort` command). When every piece is final, one `VizierRequestContent::BackgroundReport` is sent into the originating session — it runs through the `Chat` arm (history, `ThinkingStart`) with zero auto-context passages, is queued behind a running turn like any request, and frontmatters as `sender: background`. Its response sender republishes frames onto the session-event broadcast, so the woken reply streams into an open WebUI topic, and the Discord/Telegram readers pick up their own channels' woken turns from the same broadcast (`channels/woken.rs`) and post them through the renderer a person's turn uses. Every other conversation (task, dream, inter-agent, subagent) is woken into history only; `crates/vizier-core/src/agents/background/` never branches on `VizierChannelId`. `list_background_jobs` / `cancel_background_job` (and `POST …/topic/{topic}/jobs/{id}/cancel` for the tray) share `BackgroundJobs::cancel`, which aborts the pieces, cascades to jobs launched from the pieces' sessions, and never sends a report. Exactly-once is a guarded SQL transition out of `running`: the runner moves to `reporting` *before* delivering, so a job is either reported or cancelled, never both. Nesting is `VizierRequest.background_depth` (on the request, not the session — a woken turn shares the launcher's session), copied into `ToolContext.background_depth`; `launch` refuses at `MAX_BACKGROUND_DEPTH` (3). None of these tools are in `DREAM_TOOL_NAMES`; `consult_agent` is unchanged and still blocking.


**Asking the person** (`specs/042-agent-asking-question/`): two tools that answer one need — the agent needs something from somebody — and differ only in where the answer goes. `ask_question` (`questions/tool_question.rs`, category `questions`, **turn-ending**) asks 1–10 typed questions (`text`, `choice`, `multi_choice`, `confirm`) stored as a `question_set` row plus a `SessionHistoryContent::QuestionSet` entry that carries the set's `set_id` (the history row's own uid is not the set's); the entry's `state`/`answers`/`answerer` are filled from that table by `set_id` on every history read, exactly as `client_tool_call` fills a client call's outcome, which is why a pending card survives a reload, a second tab and a restart. The answer comes back as the person's next turn: `VizierRequestContent::QuestionAnswer`, an ordinary request with no bypass. `ask_sensitive_input` (`questions/tool_sensitive.rs`, category `secrets`, **not** turn-ending, WebUI only) blocks the running script on a `oneshot` and arms the value into the turn's `SecretRedactor` the moment it arrives, so the report, history entry, model copy, log line and telemetry are scrubbed as for `get_secret`; the `sensitive_ask` row holds no value. Availability is per turn: `VizierTool::available(ctx)` takes a tool out of the catalogue, out of the category lines and out of a script's reach, and `ToolContext.interactive` (`is_interactive_turn`) is the whitelist over request kind and conversation that decides it. Channels present questions through `QuestionSurface`, registered by each reader while it runs with a **weak** reference so it stops with the reader; a control carries only `<short>.q<index>.<action>`, which is why a press resolves from storage after a restart and fits Telegram's 64-byte `callback_data`. `questions/text_form.rs` is the fallback grammar for sets native controls cannot hold.

**Client tools** (`specs/019-client-tools/`, `crates/vizier-core/src/agents/client/`): a WebSocket client may declare tools of its own on any request (`VizierRequest.client_tools`/`client_categories`, `skip_serializing`, so never stored). `handle_socket` checks them (`client::declare::validate`, refusing with `client_error` before any turn starts), then swaps them for `VizierRequest.client` (`ClientBinding`: the declarations plus that socket's `ClientConnection`, `#[serde(skip)]` like `trace`). Only `VizierAgent::chat` turns them into tools: at turn start, if the connection is still open, `ClientTools::resolve` names them against `router.catalogue()` with the MCP rules (`client_category_name` → `_client` suffix on a clash with a built-in category, addon id or MCP server; `assign_names` for `_2`, `_3`), sends `client_tools_resolved`, and sets `ToolContext.client`. Every other `ToolContext` is `client: None`, which is what keeps dreams, handovers, tasks, background reports/pieces and inter-agent turns client-free. Scripts reach them through `tools::turn_catalogue`/`turn_categories` (router's, then client's), read by `RouterBridge`, `list_tool_functions` and `describe_tool_function`; `ToolTarget::Client` is dispatched by `RouterBridge` to `ClientTools::call`, never by the router. A call is saved as `SessionHistoryContent::ClientToolCall` **when made** (its history uid is the call id; skipped by `history_entries_to_messages`), written **directly** to the declaring connection (other sockets get an `answer: false` display copy via `SessionFrame::ClientToolCall`), and awaited under its timeout; a drop guard records `cancelled` if the turn is aborted. A declaration may set `deferrable`: a call made while the declaring socket is gone (or that drops before answering) becomes `deferred` (`defer_client_call`) and the script gets `{"status": "deferred"}`; `handle_socket` delivers deferred calls to the first socket on the session (on connect, and on `SessionFrame::ClientCallDeferred` for an already-open tab), claimed through a **lease on the stored row** (`client_tool_call.claimed_by`/`claimed_at`, one conditional update, so exactly one gateway delivers a call and an abandoned claim lapses - #163); deferred calls survive restarts (the startup sweep touches only `pending`) and their later result is never reported to the agent. Outcome and saved state live in the `client_tool_call` table (`ClientCallStorage`), filled into the entry on every read by `fill_client_calls` (like `fill_reactions`), deleted with the topic/agent, and swept to `interrupted` at startup. `VizierRequestContent::ClientEvent` (`client_event`: text, data, source call) starts a turn like `Chat`, frontmattered `sender: <person>`, `via: client_event`; it and `client_call_state` saves are rate-limited per conversation/call by the `RateLimiter`s on `HTTPState`. The WebUI registers its tools with `registerClientTool` (`webui/app/lib/clientTools.ts`), declares them on every request in `connectionStore`, and draws `turn.clientCalls` (from `groupHistory`, filtered by each registration's `renderAfterTurn`/`latestPerTurn` through `visibleClientCalls`) inside the reply bubble; its built-in tools are `ui_components` and `ui_render` in category `ui` (the **generative UI**, `specs/026-generative-ui-terminal-tools/`, below), and the retired `render_interactive_ui`, kept `declare: false` so saved pages still draw through `InteractivePage.tsx` (an `<iframe sandbox="allow-scripts" srcdoc>` with a CSP and a `window.vizier` bridge; tracked in #82). A client tool is named `<category>_<tool>`, so the registrations are `components` and `render` in `ui`. The public protocol is `docs/src/api-integration/client-tools.md`; `scripts/client-tools-e2e.mjs` checks it end to end against a dummyplug agent.

**Turn-ending tools** (`specs/026-generative-ui-terminal-tools/`): `VizierTool::ends_turn()` (default `false`) and `ClientToolDeclaration.ends_turn` make a **successful** call the turn's final answer. Everything is called from `execute_python`, so the loop never sees the flagged call: `RouterBridge` stamps each `ToolInvocationRecord.ends_turn` (not for a `deferred` result) from the dispatched `CatalogueEntry`, `ExecutionReport::ended_turn()` / `ending_call()` read it, and `prompt_with` ends the turn after a round whose report has `ok` and a successful flagged call: the round's results are saved, no closing completion or checkpoint is requested, the reply text is the step's own text, and `VizierResponseStats.ended_by_tool` names the function. It is stateless, so `ending_tool_in` finalises a resumed turn the same way; `chat_turn` then flushes every new message instead of holding the last back. A failed call, a failed script, a timeout or a deferral leaves the turn running. `ENDS_TURN_NOTICE` is appended once to a flagged entry's description where the definition is built (`with_ends_turn_notice`, in `ToolRouter::catalogue()` and `ClientTools::resolve`), never to `SANDBOX.md`, and the declaration's 2 KB limit counts the author's text only. Spans carry `vizier.tool.ends_turn` and `vizier.turn.ended_by_tool`.

**Generative UI** (WebUI only, `webui/app/lib/generativeUi/`, `docs/src/api-integration/generative-ui.md`): `ui_render {title, spec}` draws a json-render spec built only from the catalogue and ends the turn; `ui_components` teaches the catalogue on demand, so no skill and nothing in the system prompt. The catalogue is one source (`catalog/`, a zod entry per component with a description and example; `registry/` has one renderer per entry, and `registry.test.ts` pins that they match): it validates (`validate.ts`: every problem at once, with JSON paths, valid options and nearest names, never the spec), draws, builds `ui_render`'s `type` enum and generates the agent's reference (`reference.ts`, ≤ 24 KB) and the recipes (`recipes/`, every one validated in CI). `GenerativeUi.tsx` draws one saved call: the spec is the call's `args`, the page state its saved state (`state.ts`: `_`-prefixed keys never saved, 500 ms coalescing, remote merges not counted as local). `watch` is ours (`watch.ts`), not json-render's, so a merge from another tab does not fire it and a watch chain is untrusted and cannot loop on its own writes. `sendMessage` (`actions.ts`) needs a trusted gesture (`trust.ts`: every emitted event records whether a real DOM event started it, fail-closed), at most 1/s. `logic` functions run in a **worker inside a sandboxed iframe** (`logic/`: `host.ts` queue and 250 ms limit, `runnerSource.ts`): the worker, not the frame, because a loop in a sandboxed frame can share the page's thread and freeze it. Links follow `links.ts` (https/http/mailto, host disclosure); media refer to session files by name (`media.ts`). `three` and `@react-three/fiber` are only imported by `registry/three.tsx`, loaded through `React.lazy` (`scene3d.tsx`). A test that draws design components needs `app/test/oneReact.ts` (one React for the app and the design library).

**Adding a new tool**: create `crates/vizier-core/src/agents/tools/<name>.rs` implementing `VizierTool` (pick its `ToolCategory`; override `ends_turn()` only for a tool whose result is the reply, and add it to the `every_tool_is_in_its_category` table), add `mod <name>;`, then `.tool(YourTool)` it onto `default_toolset` or `user_toolset` inside `BaseTools::new()`. If it should be available to the dream cycle, add its name to `VizierTools::DREAM_TOOL_NAMES`. **Adding an addon** (or any integration kind): implement `IntegrationKind` in `crates/vizier-core/src/integrations/kinds/<id>.rs` (`listing` is its catalogue tile and settings form; `contribute` returns its tools with `addon: Some(id)`, each named `<id>_…` and returning `None` from `category()`), add an icon to `crates/vizier-http/assets/integrations/`, and register it in `IntegrationKinds::builtin()`. No agent-form, API or page change is needed.

### Integrations (`crates/vizier-core/src/integrations/`, `specs/016-integrations-section/`, `specs/017-agent-self-integrations/`)

Discord/Telegram bots, addons (Brave Search) and MCP servers are **integrations**, never fields on `AgentConfig`. **Each belongs to exactly one agent** (017): it is linked once, when created on that agent (`IntegrationStorage`, tables `integration` + `integration_attachment`), never attached elsewhere, and deleted with the agent. `PUT …/attachment {attached:true}` is `410 attach_removed`. Rows from 016 still linked to several agents (or none) are **legacy**: they keep working for each linked agent, only all-agents managers may change them, and deleting one from an agent's page only unlinks that agent (`unlink`); there is no data migration. Every kind implements `kind::IntegrationKind` (validate, redact/merge secrets, `missing`, `contribute`, `reader`, `platform`); nothing branches on a kind id. Rules enforced in the storage transaction: one connection per platform per agent and a token used once per platform (`409 platform_in_use_on_agent` / `token_in_use`), one configuration per addon per agent (`409 addon_installed`), no two MCP servers with the same name on one agent (`name_in_use_on_agent`; names are *not* unique install-wide). **Every write goes through `integrations/service.rs`** (`create`/`update`/`delete`/`set_grants`, taking an `Actor::Person` or `Actor::Agent`), used by the HTTP handlers and the agent tools alike: it validates, saves with its `integration_event` row (who — a `Requester` — what, which setting *names* changed, never values; the agent's session) in the same transaction, and publishes `IntegrationChanged` on the transport *after* commit; subscribers re-read storage (level-triggered). `AgentHost` sends each affected agent's running instance a `refresh_integrations()` (via the supervisor's `CurrentAgent` handle, never the request queue) — an integration change never restarts an agent or aborts a turn. Channel readers are process-wide in `channels/connections.rs::ChannelConnections` (owned by `ChannelReaders`, which `VizierRuntime` runs), reconciled against storage at startup and on channel events; they never stop or start with an agent instance, and a `FatalChannelError` marks only that connection failed until its token changes. Reader health lives on `deps.channel_board`, which feeds `AgentHealthStatus.channels`. Access is decided only in `integrations/access.rs`: `all_agents:integrations:manage` manages every agent's integrations, `owned_agents:integrations:manage` those of the agents the person owns; **who created an integration grants nothing** (the 016 `shared`/`owned` scope is gone; the column stays, unread). `creator` (a `Requester`) is kept for display only.

**Agent self-management** (017): three per-agent **grants** (`integration_grant`, one row per family `mcp`/`addon`/`channel` switched on) let an agent manage its own integrations of that family through five code-mode tools in category `integrations` (`list_integration_kinds`, `list_integrations`, `create_integration`, `update_integration`, `delete_integration`, in `agents/tools/self_integrations.rs`). Grants live outside `AgentConfig` on purpose: `PUT /agents` rebuilds the agent and aborts its turns, a grant change only publishes `IntegrationChanged` (empty `integration_id`) so the tools recompose. Only someone who manages the agent's integrations may change a grant (`PUT /agents/{id}/integrations/grants`); `POST`/`PUT /agents` refuse a `self_management` key with `422 use_grants_endpoint`. The tools are contributed by the integration layer (`IntegrationTools.self_management`), so an agent without grants has no `integrations` category at all; each call re-reads the grants, acts only on the agent's own non-legacy integrations, and is absent from `DREAM_TOOL_NAMES`. Disabling or deleting the channel connection the current conversation is on succeeds with a `warning`. HTTP: `/agents/{id}/integrations` (list/create, `DELETE /{iid}`, `/grants`, `/events`) and `/integrations/{id}`, `/integrations/kinds`(+`/{id}/icon`, public). `POST`/`PUT /agents` refuse the 016 moved fields with `422 moved_to_integrations`.

### Notifications (`crates/vizier-core/src/notifications/`, `specs/029-webui-notifications/`)

The WebUI's notification inbox replaces the old Home "Since you were away" feed. It is **persisted, not derived**: the `notification` table holds one row per notable event (`event_key` `UNIQUE`, the exactly-once guard; `agent_id`, `audience_user_id`, `category`, `tone`, `summary`, `href`, `created_at` in ms) and `notification_read` holds one row per person who read one (`user_id`, `notification_id`, `read_at`; `ON DELETE CASCADE`) — **unread is the absence of a read row**, so new rows need no per-person fan-out. `audience_user_id` is `NULL` for every agent-wide category and set only for `chat_reply`, a WebUI conversation's reply that belongs to the one person whose conversation it is; the audience is checked in the same visibility clause as `agent_id` on list, counts, per-id read and mark-all. `NotificationStorage` (`storage/notification.rs`, `storage/sqlite/notification.rs`) owns every query: idempotent batch insert, visibility-aware list/counts/read/read-all, closed-hour reply aggregates, retention purge and the startup orphan cleanup. `delete_agent` deletes the agent's rows in its transaction. List/count always filter `created_at >= now - 30 days` and `agent_id IN (visible whitelist)`; the HTTP handler resolves `visible_agents` before every call, so revocation is immediate and another agent's row is `404`. Retention is purged at startup and once a day from the scheduler's minute tick. A cursored page is `(created_at, id)` descending with an opaque base64 cursor (`notifications/cursor.rs`).

**One creation path**, `crates/vizier-core/src/notifications/mod.rs::Notifications` (on `VizierDependencies`): task runs (`scheduler`, on close/recovery/dispatch failure, and the startup sweep it now returns rows from), dream cycles (`scheduler/dream`, entries > 0), background jobs (`agents/background`, terminal states only — never `reporting`, including cancel/undelivered/recovery/startup sweep), integration writes and grants (`integrations/service.rs`, after commit, actor name resolved once, never a setting value), an agent's ready outcome and start-failure episode (`agents/supervisor.rs`). Wording lives only in `notifications/text.rs`; every call is best-effort (a failure is logged, never propagated). A completed WebUI turn notifies as `chat_reply` from the `Chat`/`AudioChat`/`ClientEvent` arm of `agents/process.rs` (a saved `Message`/`AudioReply` with a `history_uid`), addressed to the session's `HTTP(username, …)` owner; `BackgroundReport` turns are excluded (the job already notified) and Discord/Telegram stay on the aggregate. Discord and Telegram activity creates **no** notification (`VizierChannelId::platform().is_some()`, checked in `job_ended`; `chat_replied` needs a `web_user()`), and the old hourly `channel_replies` projection and its rows are gone (deleted in `init_notification_schema` and PostgreSQL migration `0003`).

**Setup is split**: live progress (phases, downloads, bytes, ETA) stays ephemeral in `SetupBoard` and `GET /utils/setup-state` (which now carries `SetupState.name`); only outcomes become rows. A successful build records `agent_setup_ready` when that build started a download (a monotonic per-agent `download_epoch` snapshot around the build) **or** the supervisor is recovering from a failure episode; a download-less quick restart/config save records nothing. A failure opens one `agent_start_failure` per episode (`{agent}:{episode uuid}`), retries reuse it, a successful start clears it, and a delete/shutdown stop records nothing. The setup board's own `failed` phase never creates a duplicate.

**The inbox stream** (`specs/051-realtime-notifications/`): notifications and setup status are pushed, not polled. `GET /api/v1/inbox/stream` is a push-only WebSocket (the desktop app drives the same `vizier_http::inbox::InboxConnection` through `inbox_open`/`inbox_close` and `Dispatcher::open_inbox`). Frames are `hello` (counts, `latest_id`, setups), `notification`, `read`, `setup`, `setup_cleared` and `resync`; the contract is `specs/051-realtime-notifications/contracts/inbox-stream.md`. Events travel the Fleet bus on `inbox.events` (`transport::InboxEvent`, a third arm of the pump in `transport/events.rs`; `Notifications::install_transport` announces each inserted row, `SetupBoard::install_inbox` announces setup). **Who may be told what is decided per delivery in `service/inbox.rs`** (`judge` is the pure rule, `deliver` re-resolves the person and reads counts once per batch), sharing `setup_state::can_see_setup` with the REST path. `download_progress` is throttled to 250 ms per agent; every other setup transition is immediate. The socket has no idle deadline (the chat socket's would drop every quiet inbox), pings every 30 s, and closes at the token's expiry (`auth::middleware::TokenExpiry`). Recovery needs no replay buffer: the table is it, `hello.latest_id` says whether to read it, and a lagged connection is sent a fresh `hello`. Rows carry `source_session` (JSON, not sent), `source_title` and `excerpt` (`notifications/excerpt.rs`, built from the *saved* entry via `HistoryStorage::get_session_history_entry` so redaction has applied); `title` is filled on read by `service::notifications::fill_titles` and withheld, with the excerpt, for another person's conversation. Deleting a conversation deletes its rows and publishes `InboxEvent::Stale`. The WebUI handles frames in the pure `lib/inboxFrames.ts`; `stores/notifications.ts` opens the stream and `stores/agents.ts` holds setup (a finished setup is dropped client-side after 5 s). No timer polls either any more.

HTTP is `/api/v1/notifications` (list with `filter`+`before`+`limit`, `/count`, `PUT /{id}/read`, `POST /read-all`, and `GET /chats` + `POST /chats/read`: a person's unread `chat_reply` rows per conversation, the counts on rail tiles and session rows; opening a chat reads it), all under `require_auth`. The WebUI has one Zustand store (`stores/notifications.ts`, fed by the inbox stream), pure merge/filter helpers (`lib/notifications.ts`) and a small popup (`screens/notifications/NotificationsPopup.tsx`, a design `Floating` aligned to the bell's right edge, `useDismiss` with the bell as `ignore`, mounted once by `AppShell` in both layouts; the old sliding panel and `ShellFrame` `aside` use are gone). The popup is one line of filters (Unread, All; the REST `read` filter stays for other clients) with mark-all and ×, then setup rows, then the list, then Load older; setup (`SetupItem`) and notifications (`NotificationItem`) are design components in one card shape, drawn on the `Notifications popup` page of `Vizier.figcraft`. The bell registers itself as the popup's `anchor` in the store and toggles it; with no bell mounted the popup hangs from a fixed point at the top right. The bell lives at the right end of every page header (`screens/shared/NotificationsBell.tsx`, mounted by the shared `PageFrame`/`SettingsFrame`, Home's header, the chat header and the mobile top bar), so a count badge and a separate busy dot are `design` `IconButton` props. Each row is a bordered card with a 34px `Sigil`; its read toggle is a check beside the time (always visible, faint once read, pressing it again marks unread; mark-all is the double `check-check`), an unread card is outlined in the live emerald and a hidden word says so. A `chat_reply` for the conversation on screen is auto-marked read with no toast or badge change (`isViewing` + `viewing` on the store, set from the pathname); the popup closes on Escape, an outside press or its ×, and the chat details panel starts collapsed. A new arrival while the panel is closed raises a timed `Toast` (design `Toast`'s `onSelect`; one toast per burst) pushed from `screens/shared/NotificationToasts.tsx`, which the stream feeds by id above `lastSeenId`. The panel is reached from no route and adds no sidebar item. The panel is not a route; opening marks nothing read, selecting a row marks it read and navigates. Home's `AwayFeed` and the `/api/v1/overview/feed` endpoint are **removed** — a deliberate breaking change; the unused visit tracking (`record_visit`, `last_seen_at`, `previous_visit_at`) stays for #82.

### Workspaces (`specs/053-workspace-channel/`, `crates/vizier-core/src/workspaces/`, `service/workspaces.rs`, `docs/src/configuration/workspaces.md`)

A **Workspace** is a shared space for people and agents, with topics. Agents read silently and are activated only by `@<agent-id>`; `consult_agent` and `delegate_agent` are gone (names in `RETIRED_TOOL_NAMES` answer with guidance) and `mention_agent` is the one way agents address each other. The channel is `VizierChannelId::Workspace(id)` (slug `workspace__{id}`, UUID ids); each member agent keeps its **own session per topic**, so each has its own record.

- **Shared timeline.** `workspace_entry` holds only *shown* messages (kinds person/agent/note), written inside `save_session_history` through `index_history_entry`; tool calls and thoughts stay in each agent's history and reach the page as `steps`. Mentions are parsed against members (`workspaces/mentions.rs`: code, quotes and strangers do not count) and move pending → woken | unavailable | dropped.
- **Silent reading is free.** `catch_up` is lazy: when an agent is activated (and before a dream cycle, `scheduler/dream`), unread entries are copied into its history as `SilentRead` rows (cap 500) in one transaction that also moves `workspace_read`. No model call, no `session_turn`, no usage.
- **Replay order.** A copied `SilentRead` keeps the entry's time, so one written during another turn's tool call is stored between that `ToolCall` and its `ToolResult`. `history_entries_to_messages` holds such a request until the round's results are in, because providers refuse a user message there. Blank narration (some models send `"\n\n"` beside every call) is neither saved nor replayed, and `groupHistory` ignores rows saved before that.
- **Files and reactions.** `PostRequest.files` are ids from `POST /files/upload`; `service::post` records them on the entry and as a session file in each member agent's session, and `wake` passes them as attachments. Reactions are `POST …/topics/{tid}/reactions`, reach sockets as a `reactions` frame, and go through `channels::reactions::apply`.
- **Activation** is an ordinary `Chat` request carrying `workspace_entry` metadata, sent by the `Hub { storage, transport }` engine. Stop-all records `workspace.stopped_at_seq`, so a turn finishing later cannot restart a chain; there is no chain limit otherwise.
- **Commands** are `/<command> @<agent-id>`, people only (`workspaces/commands.rs`); `/btw` and `/clear-files` are refused, `/lobotomy` needs edit rights on the agent. A plain mention never parses as a skill (`reads_skill_commands`).
- **Access.** Everything answers `404` to a non-member. Adding an agent needs the right to edit it (it shares its tools, provider budget and memory with all members). Names are trimmed and lower-cased before validation. Permissions: `workspaces:create`, `all_workspaces:manage`; the seeded `superadmin` role is topped up at startup.
- **Notifications.** One row per shown message (`workspace_message`, `agent_id = workspace:{id}`), none for the author or for notes. The service adds each person's Workspaces to their visible scope, so membership, not agent access, decides who is told. Per-topic unread comes from `href`.
- **Tools** (`agents/tools/workspaces.rs`, category `workspaces`): `mention_agent`, `send_message_to_workspace`, `list_workspaces`, `read_workspace_messages`. The last three work from any conversation (to be tightened by a later spec) and are not in `DREAM_TOOL_NAMES`.
- **Client.** `lib/workspaces.ts` (`buildTimeline`), `workspaceFrames.ts`, `stores/workspaces.ts`; the topic socket is `.../topics/{tid}/stream`. Mid-turn messages render in every chat, not only here.
- **Checks.** `scripts/workspace-e2e.mjs` (needs the `say` key of `dummyplug`), `tests/workspaces_service.rs`, `tests/conformance/groups/workspaces.rs` (vectors must not change state: the harness sends each twice).

### Projects (`specs/040-projects-mode/`, `specs/041-project-coding-workspace/`)

A **project** mounts one host folder to exactly one agent (`project` table behind `ProjectStorage`;
`crates/vizier-core/src/projects/`). A project chat is its own channel kind,
`VizierChannelId::Project(username, project_id)` with slug `project__{user}__{id}` (040 stored it as
`HTTP(user, "project__<id>")`; `projects::migrate::migrate_project_channels` rewrites every stored
slug/JSON once at startup under `migration.project_channel_v1`, and is tracked on #82). The web wire
`channel_id` is unchanged (`project__<id>`); `VizierChannelId::from_web(user, channel_id)` is the one
constructor, `web_user()` the one "the person in this chat" accessor, and `web_channel_id()` the wire
id. `projects::channel` keeps only the wire prefix (`PREFIX`, `channel_id`, `project_id`) and path
helpers; `projects::access` is the only permission matrix (`all_agents:projects`,
`owned_agents:projects`; management is the project owner or the all-agents permission; creation
requires a desktop principal). `service/projects.rs` owns the DTOs, folder validation (canonical,
must exist, never the app workspace or inside it), soft removal (`turn_active` while a turn is
pending), the mode, file suggestions, git and worktree operations; routes live in
`crates/vizier-http/src/api/v1/agents/projects.rs`.

`projects::context::for_turn(deps, session, request)` replaces 040's `for_session`: a `Project`
session resolves the project, the topic's worktree as `cwd`, the saved mode and a git probe; a
`Subagent` piece with `VizierRequest.project_scope` (set only by
`BackgroundJobs::dispatch_piece`) resolves the same project under the launching turn's mode and
re-checks the owner's permission. It is resolved once per turn and passed to the system prompt
(`agents/agent/system_prompt/project.rs`, stable per chat) and to `ToolContext.project`. Volatile
state (mode, branch, shell switch, folder availability) goes in the per-message `## Project state`
section of `context_md` (`system_prompt/context.rs`, `context_md_with`), never the system prompt, so
a switch cannot invalidate the prompt cache for the history.

**Coding tools** (`crates/vizier-core/src/projects/tools/`): one `REGISTRY` (`ProjectToolSpec {
access: Read|Plan|Write|Command, needs_git, tool }`) decides `offered(project)` for the turn,
`call(name, args, ctx)` refuses a name not offered (`tool_not_offered`), and `output_schema` serves
docs. `turn_catalogue` appends the offered entries, `turn_categories` adds `coding` whenever a
project context exists (both modes and an unavailable folder, so `SANDBOX.md` is stable);
`RouterBridge` dispatches `ToolTarget::Project` to `projects::tools::call`, and `docs_tools` asks the
registry for output schemas. Plan offers reads plus `propose_plan` (an ending tool); Build adds
`write_file`/`edit_file` and `workspace_shell` when the shell switch is on. `workspace_shell`
(`projects/shell.rs`) is now category `coding`. Paths go through one `projects::path::resolve`
(refuses absolute paths, `..`, symlinks out, and `.vizier/` from the root); walks use `ignore` with
hidden files shown and `.git/`/`.vizier/` skipped (`projects/tools/walk.rs`). `edit_file`/`write_file`
check `ProjectReadLedger` (`projects/ledger.rs`, on `VizierDependencies.project_ledger`, in memory,
1,024 entries per session); a read, a write or an `@` mention records the file's sha256. `@` mentions
resolve at turn start into `## Mentioned files` (`projects/mentions.rs`, never stored) and
suggestions come from `projects::suggest` (10 s per-folder cache, hand-rolled scorer).

**Git** (`projects/git/`): `Git { dir }` runs argv only, `-C`, `core.quotepath=off`, no color,
`GIT_TERMINAL_PROMPT=0`, `GIT_OPTIONAL_LOCKS=0` for reads, `LC_ALL=C`, a 15 s timeout with kill; `probe`
is `rev-parse`; `status.rs` holds the pure porcelain-v2/numstat/branch/log parsers; `worktree.rs`
appends `/.vizier/` to `info/exclude`. git is optional: absent git or a non-repository hides every git
surface (`GET …/git` answers `{available:false}`) and leaves the file tools working.

**Language intelligence** (`specs/054-project-lsp/`, `projects/lsp/`, `docs/src/configuration/projects.md`): language servers for project chats. `LspHost` (on `VizierDependencies.lsp`) owns one process per `(project, root, language)`, started in a spawned task the first time a tool reads, edits or asks about a file (`ensure` never waits) and bounded by `lsp.max_servers` (6; LRU eviction, `Availability::Busy` when every server has a question in flight; a 10-minute idle sweep). A `closed` set (switch off, project removed) refuses starts so a racing turn cannot leave a server behind. `languages.rs` is the table of 16 languages and their root rules (data, never a `match` on a language id); `search_path.rs` looks the command up on `PATH`, the login shell's `PATH` and well-known folders, never in the project folder, and removes secrets from the environment; `server.rs` is one process (hand-written JSON-RPC in `rpc.rs`, `position.rs` for 1-based scalar columns versus `utf-8`/`utf-16`, server requests answered per R11 including `applied: false`); `sync.rs` keeps documents in step by sha256 and snapshots the tree to send `didChangeWatchedFiles` after `workspace_shell` or a branch switch. `edit_file`/`write_file` call `tools::after_write`, which adds a `diagnostics` field (`diagnostics.rs`: pull where `diagnosticProvider` exists, otherwise a versioned or post-sync push, 3 s, and `current` is claimed only when an answer reflects this edit and no `$/progress` is open); `read_file` only warms the server. Five `lsp_*` registry tools (`needs_lsp`, offered in Plan and Build while the switch is on) return `status` results, never errors. The switch is `project.lsp_enabled` (new projects on, old rows off, tracked on #82) and `project_lsp_override` (env encrypted); `service/project_lsp.rs` owns status, overrides and restart, and `InboxEvent::ProjectLsp` / `InboxFrame::Lsp` push the status (coalesced to 250 ms per project) to people who can use the project. The WebUI panel is `screens/chat/LspPanel.tsx`; the strip item is `StatusStripItem { id: "lsp", dot, display }` in `design/`. The system prompt holds one fixed sentence (`LSP_GUIDANCE`); the switch itself rides in `## Project state`. Vizier never installs a server. Tests: `tests/lsp_host.rs` and `projects/tools/lsp_tests.rs` use `examples/fake_lsp.rs`; `tests/lsp_real.rs` runs clangd and rust-analyzer when installed.

**Mode and worktrees**: `project_chat (agent_id, channel, topic, mode, updated_at)`, no row meaning
`plan`, written only by `PUT …/mode`; deleted with the topic/agent. `project_worktree` binds one row
to one `(project_id, topic)` at `{root}/.vizier/{agent_id}/{name}`; creating it writes the row and the
chat's `session_detail` in one transaction, deleting it removes the folder/branch then the chat via
`SessionFiles::delete_conversation`; the ordinary topic delete delegates to the same path.
`project_has_main_turn` is the branch-switch guard for the main folder. The WebUI adds the composer
mode toggle (with "applies to the next message"), the plan card, the branch chip and changes panel,
the worktree dialog/delete confirmation, sidebar branch labels, and `@` mentions; `ProjectSession`
carries `mode`/`worktree`.

Project sessions are excluded from `conversation_rows` and `kind_of`; notifications link to
`/<agent>/projects/<id>/chat/<topic>`; usage reports `UsageActivity::Project` (label **Projects**,
place `project:<slug>:<topic>`, link to the project chat). History, files and the chat socket use the
existing channel routes with the project `channel_id`.

**Project skills** (FR-035–FR-043) are the third skill scope: `crates/vizier-core/src/skill/scopes.rs`
(`SkillScopes::for_turn(workspace, agent_id, cwd)` → project `.agents/skills` then `.claude/skills`,
agent, global; one entry per slug; `ScopedSkill` carries its folder and a bounded, confined
`resources()`). It is the **only scope outside the workspace**, so it is read where it lies and
**never indexed** — `recommend_skills` runs before a turn's project is resolved and the vector table
has no session identity. The four reading tools (`use_skill`, `list_skills`, `get_skill_details`,
`read_skill_resource`) resolve scopes from `ToolContext` per call, never in `new()`; the writing
tools stay workspace-scoped; `execute_skill_resource` refuses in a project chat (use
`workspace_shell`). The prompt lists them in `## Project Skills` (`system_prompt/project.rs`), and
`/name` resolution in `agents/process.rs` passes the same scopes. `SkillManager::scan` reports a
folder it cannot read instead of dropping it, and `Skill::author` is optional while `version` is a
`SkillVersion` (number or string) so ecosystem `SKILL.md` files parse.
### Storage (`crates/vizier-core/src/storage/`)

`VizierStorageProvider` is a supertrait composing every storage concern (`IntegrationStorage`, `MemoryStorage`, `TaskStorage`, `TaskRunStorage`, `HistoryStorage`, `SessionStorage`, `StateStorage`, `UserStorage`, `AgentStorage`, `ProviderStorage`, `CustomProviderStorage`, `CatalogueCacheStorage`, `GlobalConfigStorage`, `DreamJournalStorage`, `DreamStorage`, `SessionFileStorage`, `BackgroundJobStorage`, `UsageStorage`, `NotificationStorage`). `VizierStorage` type-erases the single `SqlStorage` implementation of those traits. `SqlStorage` runs over `storage::sql::SqlStore`; its `SqlConn`/`Dialect` boundary is implemented by SQLite and PostgreSQL, so storage behavior is shared and only SQL dialect, pooling, migrations and vector indexing differ. Do not add parallel PostgreSQL trait implementations. SQLite uses sqlite-vec; PostgreSQL requires pgvector and uses per-dimension HNSW tables.

User bytes are independent from the SQL backend. `storage::blob::BlobStore` has local and S3-compatible implementations and owns uploads, artifact versions and memory markdown. `DocumentStore` adapts memory documents onto that blob store; `BundleMemoryStore` remains the single implementation of bundle/concept logic and the sole `impl MemoryStorage for SqlStorage`. Database rows hold file metadata and the derived memory graph/passage indexes, never object content. Skills remain local installed packages. The server can select either SQL backend and either file backend independently; the desktop app is fixed to SQLite + local.

Production opens both backends through `storage::open_store` and `storage::blob::open`. PostgreSQL URLs and S3 credentials come only from environment variables/files, never serialized config or CLI values. PostgreSQL schema changes are ordered files under `storage/sql/postgres/migrations/`; SQLite keeps its existing idempotent schema initialization and compatibility migrations. `vizier storage migrate` is the offline, resumable SQLite/local → PostgreSQL/local-or-S3 cutover; it preserves encrypted envelopes, copies vectors, verifies blobs by size and SHA-256, and is tracked for pre-1.0 removal in #82.

**Passage-level retrieval** (`specs/009-memory-semantic-chunking/`): queries match **passages**, not whole documents. `storage/chunk.rs` splits a document body into structure-aware passages — `scan_blocks` (markdown blocks) then `pack_blocks` (size-packing under `ChunkLimits`, default 1200/400/2400 bytes); both are pure, sync and unit-tested, and `chunk_markdown` consults no embedder (the embedding-seam path was measured out, research Decision 1b). A third derived table, `memory_passage`, holds each passage's coordinates (ordinal, line span, byte span, `continues`, `content_hash`) — **never its text**, which is sliced from the document at query time. The `document_index` vec0 table keeps its DDL and changes only row granularity: one row per passage, keyed `{agent_id}/{bundle}/{path}#{ordinal}`. Absence of `memory_passage` rows for a document is the only marker that it is unconverted, which is what makes the per-agent conversion task resumable; drift is detected by comparing `content_hash`, not by re-chunking. `write_memory`/`delete_memory`/`delete_bundle`/`import_bundle` keep passages in step, and deletion is driven by *stored* ordinals so a shrinking document cannot orphan vectors. Passages are indexed in one batched `DocumentIndexer::add_document_indexes` call per save, with title/tags/heading-breadcrumb prefixed to each passage's index text (never to its returned text). Chunking or indexing failure is logged and never fails the save.

The one-time conversion of an existing corpus runs **per agent in `AgentHost::start`**, not in `dependencies.rs` — the indexer is built per agent from that agent's embedding config and does not exist where the other migrations run.

**Version history** (`specs/006-memory-version-history/`): CORE history lives in the `core_revision` table behind `AgentStorage` (`set_agent_core` upserts `agent_core` and records the revision in one transaction — `agent_core` is the sole home of CORE; the legacy `AgentConfig.core` field is migrated out on startup), memory history in `memory_revision` behind `MemoryStorage` (recorded inside `BundleMemoryStore::{write_memory, delete_memory, delete_bundle, import_bundle}`). Both are recorded *inside* the write path, so every caller only supplies a `RevisionOrigin` (who/why); the two kinds are deliberately separate implementations sharing only `schema/revision.rs` value types and `storage/diff.rs`. Direct on-disk edits to memory files are not versioned.

**Background jobs** (`BackgroundJobStorage`, tables `background_job` + `background_piece`, `ON DELETE CASCADE`): job and piece rows only — **no result text**; a piece's answer is the last message in its own session, read through `storage::background_job::piece_answer`, like a task run's. `dependencies.rs` sweeps `running`/`reporting` jobs and `running` pieces to `interrupted` at startup (a server restart loses in-flight jobs; the WebUI shows them as lost), and `delete_session` deletes the jobs launched from that topic.

**Encryption at rest** (`specs/031-encrypt-agent-secrets/`): `crates/vizier-core/src/encryption/` holds the one concrete `SecretCipher` (ChaCha20-Poly1305 via `ring`; fresh nonce per value; envelope `enc:v1:<key-id>:<base64url(nonce‖ciphertext‖tag)>`), key resolution (`VIZIER_ENCRYPTION_KEY` base64 of 32 bytes → `VIZIER_ENCRYPTION_KEY_FILE` → generated `{workspace}/.runtime/encryption.key`, mode 0600 where supported; never regenerate over protected data), the field helpers with record-bound AAD (`vizier:secrets:v1 \x1f table \x1f record \x1f field`), and the one-time `migrate_secrets_to_encrypted`. Protection happens **only at the storage boundary**: `SqlStorage` holds the cipher and `Arc<dyn IntegrationSecretPaths>` (implemented once by `IntegrationKinds` from each kind's `listing().fields`: `Secret` = key, `SecretMap` = `<key>.*`); `SqlStorage::new` stays the disabled-cipher constructor for tests and the filesystem import, and production uses `with_secrets`. Protected: `agent_secret.value`, provider `api_key`/`access_token`, custom-provider `api_key`/every header value, integration secret paths (unknown kind: the whole settings JSON in one envelope), and agent/global shell `env` values. Everything else stays readable, and the shell-env values remain visible in the authorized agent-config response (the one documented exception). The key is never stored in the DB, returned by an API, or written to logs/errors/telemetry; a missing/wrong/malformed key fails startup before any write, and reads never accept plaintext after the marker. Back up the key separately from the database — see `docs/src/configuration/encryption.md`. The one-time migration, its marker `migration.secrets_encrypted_v1`, the plaintext branch (`SecretCipher::open`), the pre-016 agent-key scrub and their tests are #82 removal candidates; the cipher, key sources, key id, AAD and envelope reader are permanent.

### Channels (`crates/vizier-core/src/channels/`)

`VizierChannel` trait: `async fn run(&self)`. Discord/Telegram readers are run by `channels/connections.rs::ChannelConnections`, one per enabled, assigned channel integration; each gets the small supervisor in `channels/readers.rs::supervise`: a `run` that ends is restarted with the agent supervisor's backoff, except on a `FatalChannelError` (a rejected token, Discord close codes that forbid reconnecting), which marks the reader `failed` until its token is replaced. Each reader's state shows in agent health (`AgentHealthStatus.channels`) and `vizier agent ps` (#50). Implementations: `discord/` (twilight), `telegram/` (teloxide), the HTTP server lives in its own crate, `vizier-http` (axum — REST under `api/v1/`, WebSocket, JWT auth in `auth/`, and it also serves the embedded WebUI), started by the binary through `vizier_http::serve`. A new reader is registered in `ChannelConnections`/`IntegrationKinds::builtin()`.

**Reactions** (`specs/013-reaction-awareness/`): reactions live in `message_reaction` (`ReactionStorage`), keyed by the history uid of an agent `Response` — never in the history row's `data` blob, which `fill_reactions` replaces on every read (a one-time startup migration in `init_reaction_schema` moved the old blob arrays out). A reply's uid travels on `VizierResponse.history_uid`, set by `VizierAgent::chat` after the save; the WebUI keys messages by it, and the Discord/Telegram response loops (and `discord_send_message`/`telegram_send_message`) record a `platform_message_link` row for every message they post from it, chunks and attachments included. Every channel only translates its native event and filters its own bots, then calls `channels::reactions::apply`, which resolves, checks it is an agent reply, writes, and publishes the full new set as `SessionFrame::Reactions` (the WebSocket's ack and cross-tab sync). The agent sees reactions only as the `## Reactions` section of `context_md` (`system_prompt/reactions.rs::reaction_digest`, bounded) and in checkpoint handovers — the route into the dream cycle. **A reaction never starts a turn, by decision.** Reactions on unlinked messages (people's messages, anything posted before this feature) are dropped.

### Providers / models (`crates/vizier-core/src/llm/`, `crates/vizier-core/src/catalogue/`; `specs/015-provider-catalog/`)

vizier has its own provider layer; there is no rig. `crates/vizier-core/src/llm/` is the transport: `types.rs` (`Message`, `Part`, `AssistantPart`, `ToolDefinition`, `CompletionRequest/Response`, `Usage`), `prepare.rs` (replaces attachments a model can't take with a text note, normalises system messages per dialect), five dialects in `dialect/` (`OpenAiChat`, `OpenAiResponses`, `Anthropic`, `Gemini`, `Ollama` — `encode`/`decode` pinned by golden fixtures recorded from rig 0.39), `HttpModel<D>` + `RetryingModel` in `model.rs` (backoff, `attempt_timeout`, the `prompt_timeout` deadline via `complete_until`, and `Retry-After` honoured; exhausted retries surface as `ErrorKind::RateLimited` / `ProviderUnavailable`), `auth.rs` (`CredentialSource`: `StaticKey`, `CopilotExchange`, `ChatGptAccount`), and `media/` (STT/TTS/image/embedding clients implementing the existing `Vizier*Model` traits). `resolve.rs` is the **only** place that turns `(ProviderId, model, overrides)` into a `ResolvedModel` (dialect, base URL, credential, headers, context window per research R8, caps, cost) — quirks live there and in `CredentialSource`, never as a `match` over provider ids in call sites. `VizierModel` (`crates/vizier-core/src/agents/agent/model/`) is a thin `Arc<dyn CompletionModel>` wrapper; `dummyplug` (`model/dummyplug.rs`) is the offline built-in.

**Providers are data**, from the models.dev catalogue: `crates/vizier-core/src/catalogue/` holds the seed embedded at build time (`build.rs` gzips `crates/vizier-core/assets/catalogue/api.json`; logos are embedded too), the `Catalogue` handle on `VizierDependencies` (swappable snapshot), built-ins (`builtin.rs`: ollama, llama-cpp, chatgpt, dummyplug, elevenlabs, voyageai, hyperbolic), the SQLite cache (`cache.rs`) and the lazy refresh (`refresh.rs`). The refresh is **triggered only by a person's read** (`GET /catalogue/*`, `GET /providers`, `GET /providers/custom`) or `POST /catalogue/refresh` — never by agents, the scheduler or dreams; startup makes no network request. A provider id is `ProviderId` (`config/provider.rs`, a validated string; legacy names like `gemini` deserialise to `google`). Operators can add **custom providers** (OpenAI-compatible or Anthropic protocol, any base URL, own model list; `/providers/custom`). Credentials come from the saved `provider_config` row, then the catalogue's `env[]`, then the pre-015 env var names (`provider_keys.rs`). Changing or deleting a provider's credentials restarts the agents that use it (`AgentCommand::Restart`). Replies record their provider/model in `VizierResponseStats`, which the usage API prices into `estimated_cost_usd`.

**AWS Bedrock** (`specs/034-aws-bedrock-provider/`) is the one catalogue provider with a sixth dialect, `DialectKind::Bedrock`, mapped from `npm: "@ai-sdk/amazon-bedrock"`. Chat uses the unified **Converse** API (`crates/vizier-core/src/llm/dialect/bedrock.rs`: system blocks, alternate roles with consecutive same-role messages merged, `toolUse`/`toolResult`, `toolConfig`, image blocks, `reasoningContent` only with a signature); the resolved model id is encoded as one path segment by `crates/vizier-core/src/llm/bedrock.rs::aws_uri_encode` (`:` → `%3A`) and sent unchanged otherwise. Requests are signed with **SigV4** (`crates/vizier-core/src/llm/sigv4.rs`, a pure signer over the exact body bytes; `SigV4Credential` in `auth.rs` implements the body-aware `CredentialSource::authorize_with_body`, whose default delegates to `authorize`, so other providers are unchanged; `HttpModel::send_once` and `Endpoint::post_json` serialize once and sign/send those bytes). Credentials are four fields on the same shape — `access_key_id`, `secret_access_key` (encrypted), optional `session_token` (encrypted), `region`; the listing is those four and no `api_key`; a bearer token is refused with "Bedrock API keys are not supported", a half pair names the missing field, and the region is `credentials.region` → `AWS_REGION` → `AWS_DEFAULT_REGION`, validated by `^[a-z]{2,4}(-[a-z0-9]+)+-\d+$`. The endpoint is `https://bedrock-runtime.{region}.amazonaws.com` (no `base_url`); Test signs the control-plane `ListFoundationModels` (`https://bedrock.{region}.amazonaws.com/foundation-models`), which needs `bedrock:ListFoundationModels` and no model access. Embeddings (`BedrockEmbeddings`: Titan V2 default, Titan V1, Cohere v3 in batches of 96) and images (`BedrockImages`: Nova Canvas default, Titan Image Generator V2, 1024×1024 default, MIME sniffed) share the connection through `media::endpoint`'s Bedrock branch. `SqliteIndexer::new` writes into one `vec0` table **per vector size** (`document_index` for the first model's width, so an existing install keeps its vectors, and `document_index_d<N>` for every other), and refuses a table whose declared `float[N]` differs from the model's vectors; when an agent's model changes width, `supervisor.rs::note_index_dimension` drops that agent's `memory_passage` rows (keyed `memory.index_dimension.<agent>`) so its corpus is re-indexed into the new table at the next start. The setup guide is provider data (`catalogue/guide.rs`, `ProviderSummary.guide`) rendered generically by `ConnectForm`, and the same text is the Amazon Bedrock section of `docs/src/configuration/providers.md`.

### Scheduler (`crates/vizier-core/src/scheduler/`)

Cron (`croner`, evaluated in the instance's local time, see **Time** below) and one-time task execution, plus `scheduler/dream/` — a separate periodic "dream" cycle per agent (see `dream_interval` in agent config) that runs a restricted tool subset (`VizierTools::DREAM_TOOL_NAMES`) for unattended reflection/journaling.

**Task runs** (`specs/011-task-completion-reports/`): every firing is recorded as one `task_run` row (`TaskRunStorage`), opened before dispatch and closed from the `send_request` response channel the way `DreamScheduler` already does — `answered`, `no_response` (dispatch failed or the turn produced no message) or `interrupted` (swept at startup by `dependencies.rs`, since nothing can legitimately be running before the scheduler starts). A fired one-time task is **deactivated, not deleted**; deleting it before dispatch is what used to leave nothing to hang a result on. The `running` row *is* the overlap lock, replacing an in-memory `HashSet` that was inserted and removed within one loop iteration and so never actually spanned a run. Recording failures are logged and never abort the run.

`VizierChannelId::Task::to_slug()` renders its timestamp **in full**, so each firing gets its own conversation; it used to render `timestamp_subsec_nanos()` of a second-truncated time — always `0` — so every run of a task collided into `task__{slug}__0`. A run's response is never stored: it is the last `Response` carrying message content in that run's session, read through `storage::task_run::task_run_response`. Runs surface over `GET /agents/{id}/tasks/{slug}/runs` (key-set cursor on `(ran_at, id)`) and `.../runs/{run_id}/history`, and to the agent itself through `list_task_runs` / `get_task_run_detail` (both in `DREAM_TOOL_NAMES` — `is_non_user_channel` excludes `task__` from the sessions the dream cycle reflects on, so these are the only route by which a task's outcome reaches memory).

`Task.requester` (a `Requester` enum of `User(String)` / `Agent(AgentId)`) replaced the free-form `Task.user`: `POST`/`PUT /tasks` take it from the authenticated caller and ignore any `user` in the body, and the agent tools have it declare own-initiative versus a named person. A scheduled run's system prompt gains `system_prompt/scheduled_run.rs` and its frontmatter reads `sender: scheduler` with `task` and `requested_by`.

**The one thing to get right here**: the scheduled-run framing is selected on `VizierSession::is_scheduled_task()` — the session's *channel* — never on the request content kind. `VizierRequestContent::Unattended` (renamed from `Task`, since two of its three construction sites are the dream cycle) is sent by the dream cycle too, which carries its own framing; branching on it double-frames every dream.

### Time (`crates/vizier-core/src/time.rs`, `specs/052-unify-local-timezone/`; docs: `docs/src/configuration/time.md`)

Vizier runs on **one clock: the host's timezone**. `pub type Timestamp = DateTime<Local>` replaces `DateTime<Utc>` everywhere; it compares and hashes by instant, reads any RFC 3339 offset, and writes `Z` at a zero offset, so a UTC instance's output is byte-identical. `time::init_zone()` runs first in `VizierRuntime::start`: on Unix a `TZ` must be an IANA name (a POSIX rule or a misspelling is refused), and a known name whose chrono-tz offset differs from `Local`'s means zone files are missing (chrono falls back to UTC silently), so that is refused too. A name the host reports but cannot confirm only warns. `GET /utils/timezone` returns `{name, offset}`; the Docker image installs `tzdata`.

- **Don't write `Utc::now`, `DateTime<Utc>` or `with_timezone(&Utc)`** in new code (no CI check enforces it). The only legitimate uses are `time.rs`, `llm/sigv4.rs`, `llm/error.rs` and `storage/blob/s3.rs` (external formats). A type deriving `ToSchema`/`IntoParams` must spell `DateTime<Local>` (the derive cannot see through the alias).
- **Text columns that are sorted or paged as text** (about 15, e.g. `integration_event.at`, `client_tool_call.claimed_at`) are written in UTC through `time::stored`/`stored_now`, never `to_rfc3339()` on a `Timestamp`, because text with mixed offsets does not sort chronologically. Epoch-millisecond columns are unaffected. `VizierChannelId::Task` serializes its time in UTC (`serialize_utc`) because the channel's JSON is itself a text key in several tables. A time in a message a person reads uses `time::display` (keeps `UTC` at a zero offset).
- **Scheduling input**: `time::parse_schedule` (RFC 3339 with an offset is that moment; a date and time with no offset is local; an overlap takes the earlier, a gap is `ScheduleTimeError::InGap`). Zone logic is written over `chrono::TimeZone` and tested with `chrono_tz` zones, because a test cannot change the process's `Local`.
- **The prompt carries no clock.** `context_md_with` has no `## Time`, and `boot.rs` tells the agent to ask the `time` tools (`current_time`, `convert_time`, `shift_time`, `time_between`, category `time`, on `default_toolset` and in `DREAM_TOOL_NAMES`; refusals are `status` results). A message has one stored time, `VizierRequest.timestamp`, stamped by the server on receipt (`topic.rs::stamp_on_receipt`; a client's value is discarded) and shown to agents as `sent_at` by `generate_frontmatter`, which hides an old row's own `metadata.sent_at`/`timestamp` (#82).
- **Days** (Home, usage, dream nights) follow the local day: `Dialect::day_of_millis` uses SQLite `'localtime'` and PostgreSQL `AT TIME ZONE <name>`; the `tz` query parameter is accepted and ignored (#82). The WebUI shows the **server's** zone whatever the browser's (`webui/app/lib/timezone.ts`: `zoned`, `wallClockString`), with no indicator.
- **Upgrade**: `migrate_one_time_tasks_to_local` (marker `migration.one_time_task_local_v1`, #82) rewrites only one-time tasks; cron expressions and dream schedules keep their text and now mean local time.

### Telemetry (`crates/vizier-core/src/telemetry.rs`, `crates/vizier-core/src/llm/telemetry.rs`; docs: `docs/src/configuration/observability.md`)

OpenTelemetry export is a `tracing-opentelemetry` layer next to the fmt layer, installed in `main.rs` only when `OTEL_EXPORTER_OTLP_ENDPOINT` is set (OTLP/HTTP; `OTEL_METRICS_EXPORTER=none` skips metrics). Spans therefore go through the same `EnvFilter` as logs. Span names follow the GenAI semantic conventions and are set through `otel.name`: `invoke_agent {agent}` (`VizierAgent::invoke_agent_span`, opened by `chat`/`dream_chat`), `chat {model}` (`llm/telemetry.rs`, around each `HttpModel` request, plus the `gen_ai.client.*` histograms), `execute_tool {tool}` (`tools/mod.rs`: `traced_tool_call` for the model's own calls, with the call id and the tool timeout; `ToolRouter::call` for calls made from scripts; `dream_call` uses the span-less `dispatch` because its loop already opened one), and `background_job {kind}` (`BackgroundJobs::launch`, kept open by instrumenting the runner, so pieces and the woken report turn are its children). Anything content-bearing (messages, system prompt, tool definitions, tool arguments/results) is recorded only when `llm::telemetry::capture_content()` is true (`OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT=true`): keep new content attributes behind it. Non-convention attributes are namespaced `vizier.*`.

**Trace propagation across the transport**: `VizierRequest.trace` (`telemetry::RequestTrace`, `#[serde(skip)]`, so never stored or accepted from clients) is filled by `VizierTransport::send_request` with the sender's current span context and the time it was queued; `invoke_agent_span` adopts it as parent and reports `vizier.queue.wait_ms`. So a request sent from inside a span (a tool call, a background job) continues that trace with no extra code, and one sent from a channel handler (no span) starts a new one. A new `VizierRequest` literal needs `trace: Default::default()` or `..Default::default()`.

### Usage accounting (`crates/vizier-core/src/usage/`, `crates/vizier-core/src/agents/agent/model/usage.rs`; `specs/018-usage-accounting/`)

Every answered completion is recorded by `VizierModel::complete_until` itself: one `usage_event` row (`UsageStorage`) per call, written in a spawned task so it never delays or fails the call, and never on `Err`. `complete`/`complete_until` take a **required `&UsageScope`** (`Turn` with the turn id and round, `Handover`, or `Vision`, plus the session), so a new call site must say what it is for. The activity is fixed at write time: `Handover` → compaction, `Vision` → vision, `Turn` → `VizierChannelId::usage_activity()`. The Channel-breakdown key is `VizierSession::usage_place()`. `prompt_with` and `dream_prompt` hold a `TurnGuard` (`VizierModel::guard()`); dropped without `succeeded()` (an error, the prompt timeout, an aborted task), it inserts the turn into `usage_failed_turn`. "Failed" is that join, never a column, so the mark and the turn's last insert can land in either order. `crates/vizier-core/src/usage/` builds the report: SQL groups (`UsageGrouping`), Rust prices each `(provider, model)` group with the catalogue through the one `metrics::estimate_cost(&TokenCounts, …)`, and labels and links are resolved from storage only (no platform lookups). `migrate_reply_usage` (`dependencies.rs`) copied every saved reply's stats in once as `legacy` rows and set the state key `usage.accounting_since`. Session deletion keeps usage; agent deletion removes it. Not recorded: STT, TTS, image generation, embeddings, and the provider test ping (it bypasses `VizierModel`).

### Config layering

- `.vizier.yaml` (top-level key `vizier:`) is **seed config**, read once by the binary: `cli::config_resolve::resolve` picks the file (`-c`, `$VIZIER_CONFIG`, `./.vizier.yaml`) and calls `VizierConfig::from_path`, or builds the defaults on `$VIZIER_DATA_DIR`/`$HOME/.vizier`; an embedder calls `VizierConfig::with_workspace` instead. Supports `${ENV_VAR}` expansion (`shellexpand`). `dev.vizier.yaml` is the local dev config (already has working keys — don't treat it as a template to copy secrets from).
- There is no YAML `providers` section any more: a leftover one is ignored with a warning naming the env var to set. Provider credentials live in storage (Settings › Providers, `/api/v1/providers`) or env vars. `catalogue.refresh` (default `true`), `catalogue.ttl` (default `24h`) and `catalogue.url` control the catalogue refresh (also `--catalogue-refresh`/`--catalogue-ttl` and `VIZIER_CATALOGUE_REFRESH`/`VIZIER_CATALOGUE_TTL`). Agents are **never** defined in YAML — they're created/updated only through the WebUI/HTTP API and persisted to storage.
- `AgentConfig` no longer carries `discord_token`, `telegram_token`, `tools.discord`, `tools.telegram`, `tools.brave_search` or `tools.mcp_servers` (spec 016): those are integrations. Rows saved before still load (unknown keys are ignored) and drop the keys on their next save.
- `AgentConfig` also carries `chunking` (`ChunkLimits`: `target_size`/`min_size`/`max_size`) and `auto_context` (`chat_passages` default 5, `silent_read_passages` default **0**, `threshold` default 0.6, `size_cap`, `per_document`). `SilentRead` fires for every non-mention Discord guild message and every Telegram group message, so its budget is separate and off by default — its cost would otherwise scale with channel traffic. The automatic-context threshold is provisional and meant to be derived by replaying stored session history.
- CLI flags (`--port`, `--workspace`/`--data-dir`, `--storage`, `--workers`, `--ws-idle-timeout`) override whatever the config file loaded, applied via `VizierConfig::apply_overrides`.
- Docker env vars (`VIZIER_CONFIG`, `VIZIER_DATA_DIR`/`VIZIER_WORKSPACE`, `VIZIER_PORT`, `VIZIER_STORAGE`, `VIZIER_OBJECTS`, `VIZIER_ROLE`, `VIZIER_WORKERS`, `VIZIER_WS_IDLE_TIMEOUT`, `VIZIER_JWT_SECRET`, `VIZIER_EXTRA_ARGS`) are translated to CLI flags by `docker-entrypoint.sh`, which then `exec`s the binary so signals propagate.

### Agent identity: the memory document `core/soul`

An agent's persistent "self" is a **memory**, at the address `core/soul` (`schema::CORE_BUNDLE` / `schema::SOUL_PATH`, specs/043-unify-core-and-memory). It is read, written, listed, linked, versioned and inspected with the ordinary memory tools — there is no identity-specific tool, and the `identity` tool category is gone. `core` is a reserved bundle: it holds only `soul`, cannot be deleted (not even with `force`), and refuses an import; the document inside it is deletable and updatable like any other memory. A removed soul is rendered from the embedded template with a note naming the address, never an empty block.

The document is written once at agent spawn by `BundleMemoryStore::seed_identity`, from the legacy `agent_core` row or the template, verbatim plus a provenance line, with the size cap bypassed so no upgrade is blocked. The seed runs from `start_memory_maintenance` for **every** agent — including one with no indexer, which writes through a no-op one. It is idempotent (a document present means nothing to do) and is retired with the rest of the compatibility layer before 1.0.0 (issue #82).

Memory writes are bounded by `config::MemoryLimits` (8 KiB ceiling / 4 KiB soft limit; the identity document is 4 KiB / 1.5 KiB because it is paid for every turn). Both rules live in `BundleMemoryStore::write_memory_inner`, the single write path every caller funnels through, so a tool write, an HTTP write, a rollback and an import are judged identically. Over the ceiling is a refusal carrying the overage and a split pattern; over the soft limit is a success carrying a separate `warning` field. A document already above the ceiling accepts a shorter write and refuses a longer one, so the limit is not a trap.

The product-facing term is still **Core**; only where it lives changed. `templates/CORE.md` (`constant::CORE_MD`) stays the default identity source. The `/core` HTTP API is kept as a **deprecated projection** over this document — same response shapes, one document behind both — and removal is tracked in issue #82.

## Key conventions

- **Migration & backward-compat code is tracked for removal before 1.0.0** in [#82](https://github.com/vizier-lab/vizier/issues/82). Keep it working until then: don't delete a migration, legacy shim or `legacy`/`migrated_from` field as "dead code". When you add new code of this kind (a startup migration in `dependencies.rs`, an `add_column_if_missing`/data move in an `init_*_schema`, a `Legacy*` type, a lenient deserializer, an old-name alias, or an API refusal kept for old clients), add a checklist entry to #82 naming the code and anything that depends on it.

- **Errors**: `VizierError(pub String)` (`crates/vizier-core/src/error.rs`); the crate-wide alias is `crate::Result<T> = Result<T, VizierError>`. Convert external errors with `throw_vizier_error(prefix, err)`. Avoid `unwrap()`/`expect()` outside tests and `main`'s bootstrap.
- **Logging**: `tracing` only (never `println!`) — `tracing::info!`, `warn!`, `error!`, etc. `main.rs` sets per-crate directive overrides (twilight, sqlite, reqwest, hyper, bollard, rmcp, etc. quieted to `error`/`off` by default unless `RUST_LOG` is set).
- **Extensibility is trait-based**: new tools/channels/storage backends/providers get added by implementing the relevant trait and registering the impl in its module constructor — not by branching on type inside existing dispatch code (see `.specify/memory/constitution.md` for the fuller rationale if present).
- **Conventional commits**: `feat:`, `fix:`, `docs:`, `style:`, `refactor:`, `perf:`, `test:`, `build:`, `ci:`, `chore:`, `revert:` — `type(scope): subject`, `!` before the colon for a breaking change (`[**breaking**]` in the changelog is git-cliff's rendering, not a type). Changelog is generated by `git-cliff` (`cliff.toml`). Applies to every commit message **and every pull request title**, in the workspace and in each submodule (constitution v2.1.0).
- **Matching submodule branches via `just`**: a spec branch (`NNN-short-name`) exists under the same name in the workspace and every submodule. Use the recipes, not raw git across repos: `just checkout <branch>`, `just status`, `just pull`, `just commit "<message>"`, `just push`, `just branch-rm <branch>`, `just worktree <branch>`, `just hooks`.
- **Per-agent isolation**: MCP servers and shell config live on `AgentToolsConfig` per agent, not globally — don't reintroduce a global MCP/shell singleton.

## WebUI (`webui/`)

The WebUI is the submodule `vizier-lab/webui` (spec 024), built on the `design/` submodule (`vizier-lab/design`, spec 022): React components on hand-written tokens, with a Storybook catalogue that is the source of truth for the design. A new screen or layout is drawn in FigCraft first (see **Design first** above); a change to a component is made in `design/` first, then used in `webui/`, then vizier's pins are bumped (commit order: design → webui → vizier). The previous WebUI is in `legacy/` for reference only; don't edit it.

**Dismissal convention (modals and popups)**: every modal, slide-over, popover, menu or floating panel must have a visible way to close it, and must close on Escape and on a press outside it. `Dialog`/`Modal`/`SlideOver` (design) already do all three: `Dialog` always draws a × in its header (content dialogs with `confirmLabel=""` have no other button), and backdrop presses go through `useBackdropDismiss` (the press must *start* on the backdrop, so dragging a text selection out of a field doesn't close it). Non-modal popups use `useDismiss(open, onDismiss, ref)` (Escape + outside press); don't hand-roll a `pointerdown` listener. A new popup that skips any of the three is a bug.

React Router v7 (SPA, `ssr: false`) + React 19 + TypeScript + Tailwind v4, composing `@vizier/design` only. State in Zustand stores in `app/stores/`, pure logic with vitest tests in `app/lib/` (the turn reducer `lib/frames.ts`, the trail model `lib/trail.ts`, paging), the typed API client and topic socket in `app/api/` (`schema.d.ts` is generated from the server's OpenAPI by `scripts/openapi.mjs`), screens in `app/routes/` and `app/screens/`. `npm run dev` serves on `:5173` and proxies `/api` to vizier on `:9999`. Build output (`webui/build/client/`) is what the Rust HTTP channel serves at runtime — see the `build.rs` gotcha above.

**The phone shell** (`specs/056-mobile-shell/`, below `lg`, `lib/useMobile.ts`): no bottom bar. The design `MobileTopBar` carries ☰ (or back, inside an agent), the agent (sigil, name, status: its name opens the switcher, the `sliders` button beside it opens the agent's details) and the bell, every control bare with a 44px target; on a chat a second row holds the topic, which opens the conversations as a bottom sheet (`SlideOver side="bottom"`, `AgentConversations`, shared with the desktop agent column). `AppShell`'s phone branch mounts `MobileNavDrawer` (Home, Chat, Settings, Theme, the person: the app, never an agent) and `AgentSwitcherSheet` (agents then Workspaces, each agent row with its own details button, no New agent); `stores/nav.ts` holds both open flags and `lastAgent`. `/:agentId/details` (`routes/agent-details.tsx`) is the phone's way into an agent's pages, from the design `AgentDetailsList` (the `AgentMenu` page sets; no Core row, Memory reaches it); a wide screen redirects it to `/:agentId/config`. Which rows hide or disable is `lib/agentDetails.ts`, one pure rule with tests. Every agent page goes back up to the details; the details go back to the chat. Home on a phone (`MobileHome`) is two lists, Agents and Workspaces, each with a `SectionHeading` +, no greeting and no borders. The top bar and the root pad by the safe areas (`pt-safe`/`pb-safe` in `design/`); the installed iOS app sizes the root to the tallest height it has drawn in that orientation, because the keyboard can leave `dvh` short. The drawing is the `Shell · mobile` page of `Vizier shell.figcraft`.

**Color themes** (`specs/050-user-color-themes/`, `docs/src/configuration/themes.md`): Settings › Appearance, all client side. Every UI color is a role in `webui/app/lib/themes/roles.ts`, bound to one `--vz-*` token, and `vizier.test.ts` fails if a color token in `tokens.css` isn't a role. So a new color token needs a role there, and presets get it from `derive.ts`. A scheme is inline properties on `<html>` (`apply.ts`), cached in `vizier.scheme.paint` for the pre-paint script; Vizier paints none, and `stores/appearance.ts` imports palettes only when something other than the default is in use, so the default scheme costs nothing at startup. A preview of another scheme uses design's `ThemeScope`, which sets `--vz-*` and `--color-*` together. Drawing with resolved colors? Depend on `useAppearanceKey`, not `useDark`. Code colors are the `--vz-code-*` tokens, separate from status colors on purpose.

## Website (`landing/`)

The website is the submodule `vizier-lab/landing`, an Astro 7 + Starlight site served at `www.vizier.rs`. It owns three surfaces: the landing page at `/`, the blog at `/blog`, and the documentation at `/docs`. It is not part of the Rust binary or `cargo package`; `build.rs` never touches it.

**Sources stay in this repo.** `docs/src/` is the only docs source; `scripts/sync-vizier.mjs` copies it into the Starlight collection at build time, adds frontmatter (title, edit link), strips the source H1, rewrites relative `.md` links to `/docs/.../`, turns GitHub alert markers into labelled blockquotes, and generates the sidebar from `docs/src/SUMMARY.md`. Links to files outside the docs tree (the illustrative memory links) and code-fenced links are left alone. Blog posts are authored in `landing/src/content/blog/`, not here.

**The design system is shared, not copied.** `landing/package.json` consumes `@vizier/design` as `file:./design`; `landing/scripts/link-design.mjs` creates `landing/design` as a symlink to this checkout's `design/` (the deploy workflow points it at `.vizier-source/design`). There is one design pin, on this repo. The landing build imports `@vizier/design/styles.css` and components exactly like the WebUI; only interactive pieces hydrate. The landing repo cannot build without a vizier checkout, which is already true for docs.

**Deploy.** Push to `landing` master deploys that repo's Pages site. A vizier release dispatches `repository_dispatch` type `vizier-release` to `vizier-lab/landing` with `{version, ref}` (the release tag), so the site shows that version and its docs. `vizier` needs the `LANDING_DISPATCH_TOKEN` secret (fine-grained PAT, `landing`, Contents read/write). `SITE_URL` and `BASE_PATH` come from `actions/configure-pages`, so the same build works at `vizier-lab.github.io/landing/` and `www.vizier.rs`. The deploy workflow is `.github/workflows/deploy.yml` in the landing repo. `book.vizier.rs` stays on this repo's Pages: `.github/workflows/deploy-docs-redirect.yml` replaces the old mdBook artifact with a redirect to `/docs` (run it by hand at cutover). See `landing/README.md`.

**The catalogue ships with the site.** `design/` has no Pages site of its own: every landing deploy builds `storybook-static/` from `vizier-lab/design` (the dispatched `client_payload.sha`, or `master` otherwise — deliberately not vizier's pin) and copies it to `dist/design/`, published at `www.vizier.rs/design`. A design push dispatches `repository_dispatch` type `design-updated` with `{sha}` from `design/.github/workflows/deploy-storybook.yml`, which needs the same kind of `LANDING_DISPATCH_TOKEN` secret in the design repo. Because the catalogue is built inside the site deploy, a story that fails to build fails the website deploy rather than publishing half a site.
